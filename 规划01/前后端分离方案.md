## 现状（已落地的前后端分离）

本仓库已经完成前后端分离，并在此基础上实现了 LAN 联机（权威服务端 + 客户端插值渲染）。

### 目录与职责（实际代码）

```
duel-app/src/
  backend/            # 纯模拟后端（TS），确定性 + 回归入口
  frontend/           # 渲染（p5）与 UI 表现
  net/                # LAN v1：WebSocket client、插值缓冲、联机本地粒子重建
  duel.ts             # 游戏主循环：Local/Net 两种驱动整合
  ui.ts               # 输入归一化（键盘/触控）与 UI 交互

duel-app/src-tauri/crates/
  duel-core/          # Rust 后端（与 TS 对齐）
  duel-server/        # Rust 权威服务端（CLI + WS）
```

### 边界与数据流（现状）

- 本地模式：`ui.ts` 产出输入 → `DuelBackend.step(InputFrame)` → `renderer` 渲染 `BackendSnapshot`
- 联机模式：
  - 输入：客户端发送 `input_state`（状态同步），输入包含 `moveX/moveY`（移动）与 `aimX`（长弓蓄力阶段瞄准微调），服务端每 tick 复用"最后输入态"推进后端
  - 快照：服务端固定 tick 推进，按协商的 `snapshotHz` 广播 snapshot
  - 粒子：客户端本地重建（基于 `join_room_ack.seed` 与快照序列）；联机判定不依赖粒子
  - 视角：P2 客户端可对渲染快照做本地 180° 旋转，并做对应输入映射，使双方都以"下方视角"操作

接口契约以以下内容为准（按"从硬到软"的优先级）：
- `duel-app/src/net/protocol.ts`（实际消息类型）
- [联机协议规格 v2](./联机与同步/联机协议规格v2.md)（传输层与消息格式）
- [联机系统设计.md](./联机与同步/联机系统设计.md)（系统层规则与流程）
- `duel-app/src/backend/types.ts`（BackendSnapshot / InputFrame / PlayerInput 等实际类型）

## 二、修改文件清单

### duel-app/src/duel.ts

**当前问题**：同时承担输入设备抽象、玩家/AI决策、状态更新、渲染与特效。

**改造方案**：保留为渲染器，移除玩法更新逻辑。

**改造步骤**：
1. 移除所有`act()`、AI决策、碰撞判定、回合结算代码
2. 保留`display()`相关代码，改为读取`BackendSnapshot`
3. 粒子/屏幕抖动/背景线条保留，允许随机

### duel-app/src/main.ts

**改造方案**：新的驱动方式。

```ts
import { DuelBackend } from './backend/backend';
import { DuelRendererP5 } from './frontend/rendererP5';
import { InputController } from './ui';

const backend = new DuelBackend(config, ['p1', 'p2']);
const renderer = new DuelRendererP5(p5);
const inputCtrl = new InputController();

let accumulator = 0;
const TICK_MS = 1000 / 60;

function gameLoop(now: number) {
  accumulator += now - lastTime;
  lastTime = now;
  
  while (accumulator >= TICK_MS) {
    const inputFrame = inputCtrl.getInputFrame(backend.state.tick);
    backend.step(inputFrame);
    accumulator -= TICK_MS;
  }
  
  renderer.render(backend.getSnapshot(), uiState);
  requestAnimationFrame(gameLoop);
}
```

### duel-app/src/ui.ts

**改造方案**：分离后端输入和前端UI动作。

实际类型以 `duel-app/src/backend/types.ts`（`PlayerInput`/`FrontendActions`/`InputFrame`）与代码实现为准。

## 三、API定义

### 后端输入API

以 `duel-app/src/backend/types.ts` 的 `InputFrame` / `PlayerInput` 为准。

### 后端输出API

以 `duel-app/src/backend/types.ts` 的 `BackendSnapshot` 为准。

**要求**：纯数据、可序列化、无p5/DOM对象。

以 `duel-app/src/backend/backend.ts` 的 `DuelBackend` 为准。

## 四、量化规范

### 量化时机

每个60TPS步结束时统一量化写回状态。

### 量化范围

| 字段类型 | 量化方式 |
|----------|----------|
| 位置/速度/加速度 | ×512取整÷512 |
| 角度 | 弧度×512取整÷512 |
| 冷却/无敌帧 | 整数tick计数 |
| 分数 | 整数 |

> 说明：当前仓库实现未采用该量化策略；本节保留为可选优化草案。

### 量化函数

```ts
export function q512(n: number): number {
  return Math.round(n * 512) / 512;
}
```

## 五、网络同步规范

### 状态快照下发

| 参数 | 值 |
|------|-----|
| 后端帧率 | 60 TPS |
| 下发频率 | 60 Hz（每 tick 一次） |
| 客户端插值窗口 | 33ms（约2 tick） |

### 客户端平滑

- 只插值位置/朝向等表现字段
- 不做外推预测
- 不做客户端判定

### 网络模型

权威服务器（独立 duel-server）：
- 客户端发送输入态（input_state，带 seq；不绑 tick）
- 服务端每 tick 复用“最后输入态”推进后端并广播快照（tick 递增）
- 粒子不同步：服务端下发空 particles；客户端按 seed + 快照序列本地重建粒子以保持单机观感

## 六、实现步骤

### 步骤1：抽取后端状态和步进

1. 定义`BackendState`类型
2. 实现`createInitialState()`
3. 实现`step()`：输入→更新玩家→更新箭→碰撞→回合结算→量化

### 步骤2：改造AI

1. AI只读`BackendState`，产出`PlayerInput`
2. AI内部状态不下发
3. 后端统一处理玩家和AI输入

### 步骤3：改造前端渲染

1. 渲染器只读`BackendSnapshot`
2. 粒子/抖动/尾迹完全留前端
3. 颜色/字号由前端决定

### 步骤4：重接输入管线

1. `InputController`采集键鼠/触控
2. 每tick生成`InputFrame`
3. 发给后端`backend.step(frame)`

### 步骤5：新的运行时驱动

1. 后端60tps驱动
2. 前端RAF绘制
3. 可选：前端插值平滑

## 七、验收标准

### 后端独立性

- 后端可在Node/Worker中运行
- 不依赖p5/DOM/WebAudio/Tauri API
- 同输入序列产生相同输出

### 前端只读性

- 前端只读`BackendSnapshot`
- 前端特效不影响判定
- 前端随机不影响同步

### 量化正确性

- 所有判定相关字段已量化
- 量化后数值可重现
