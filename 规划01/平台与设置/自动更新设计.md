# 自动更新设计（桌面端）

本文件定义“自动更新”的产品与工程契约。

范围：

- Tauri 桌面端（Windows/macOS/Linux）：应用内更新

非范围：

- Web：不做自动更新
- 移动端：由应用商店更新机制负责（本文件不展开）

---

## 1. 目标

- 用户无需手动下载安装包即可更新到最新版本
- 更新失败可回退到手动下载路径，并给出可解释提示
- 更新相关密钥不进入仓库，发布流程可审计可复现

---

## 2. 更新模型（桌面端）

### 2.1 用户触发

- 设置页/关于页提供“检查更新”入口
- 可选：启动后在空闲时自动检查（不得阻塞启动）

### 2.2 状态机

| 状态 | 含义 |
|------|------|
| idle | 未检查或已完成 |
| checking | 正在检查版本 |
| available | 有可用更新（显示版本号与变更摘要链接） |
| downloading | 正在下载 |
| ready_to_install | 下载完成，等待安装/重启 |
| installing | 应用更新中 |
| failed | 失败（显示原因与兜底路径） |

### 2.3 兜底路径（必须）

当自动更新失败或不可用：

- 提供“一键打开下载页”（GitHub Releases 或官网）
- 明确提示失败原因（网络、签名、权限、文件占用等）

---

## 3. 安全与发布契约

### 3.1 签名与密钥

- 自动更新必须启用签名校验
- 签名私钥只允许以 CI secrets 注入，不得写入仓库，不得出现在日志

### 3.2 Release 产物规范

- Release 必须包含：版本号、对应平台安装包、更新元数据（由实现方案决定）
- 版本号以应用配置与发布产物为准，禁止出现“代码版本与包版本不一致”

### 3.3 日志与排障

- 更新流程必须可导出日志（不包含敏感信息）
- 日志最少包含：检查时间、目标版本、下载 URL（可脱敏）、错误码/错误类别

---

## 4. 方案选择（实现侧）

本仓库使用 Tauri v2；推荐优先采用官方 Updater 能力（或官方插件生态）实现应用内更新，并保留“打开下载页”兜底路径。

实现细节（插件配置、签名工具链、CI 流水线）在落地时补充到本文件的“实施说明”章节。
