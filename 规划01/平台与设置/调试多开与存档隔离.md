# 调试多开与存档隔离

本文档记录两件事：

- 当前“调试多开（同机启动多个 Tauri 客户端进程）”的实现方式与注意事项
- 为支持调试多开而设计的“存档/设置隔离（Profile 命名空间）”方案

---

## 1. 背景与目标

产品侧目标通常是“单实例”（避免玩家误操作双开导致键位冲突、资源占用与状态混乱），但研发/QA 侧需要“调试双开/多开”来验证：

- 同机联调（A/B 两个客户端加入同一局）
- 弱网/断线重连/串房间等联机问题
- 多房间管理与房间列表 UI

因此存档系统必须满足：

- 发布版可维持单实例体验
- 调试多开时，多个进程的数据互不踩踏（设置/存档/缓存都要隔离）

---

## 2. 现状：目前没有正式的存档/设置持久化实现

截至目前，`duel-app` 已落地“设置持久化 + Profile 隔离”的最小实现：

- Web：使用 localStorage 保存设置
- Tauri：使用 app data 目录下的 `profiles/<profileId>/settings.json` 保存设置
- ProfileId：`DUEL_INSTANCE` 存在则用其值，否则为 `default`

因此本文的“隔离方案”既包含**权威约束**，也包含**已实现现状**；后续若实现发生偏离，必须先回写本文以保持一致。

---

## 3. 调试多开：当前逻辑与入口

### 3.1 启动命令

入口命令：

`pnpm -C duel-app tauri:dev:dual -- --host 127.0.0.1 --port 1420 --instances 2`

其脚本实现见：

- `duel-app/scripts/tauri-dual-dev.mjs`

### 3.2 脚本做了什么

`tauri-dual-dev.mjs` 的核心行为：

- 生成临时 Tauri dev 配置，把 `devUrl` 指向同一个 Vite 地址
- 选择性启动/复用 Vite dev server
- 在 Windows 上先执行一次 `cargo build --no-default-features`，降低并行 `cargo run` 的构建争用
- 启动 N 个 `tauri dev` 子进程，并注入实例标签
  - 环境变量：`DUEL_INSTANCE=<A|B|...>`
  - Windows 下额外注入：`WEBVIEW2_USER_DATA_FOLDER=<temp>/duel-webview2/<A|B|...>`，避免 WebView2 数据目录冲突

### 3.3 已知风险（Windows）

在 Windows 上，多开常见失败原因包括：

- 杀软/安全软件拦截或占用构建产物，导致 build script 无法执行（常见错误：`拒绝访问 (os error 5)`）
- Cargo 包缓存与构建目录锁争用导致启动顺序不稳定
- WebView2 user-data 目录被多个进程抢占导致其中一个实例秒退

如需排查，优先看 `pnpm tauri dev` 的控制台输出是否出现 `os error 5`、或持续的 `Blocking waiting for file lock ...`。

## 4. 存档/设置隔离方案：Profile 命名空间

### 4.1 关键原则

- 发布版默认走 `profileId=default`
- 调试多开时，每个进程用不同 `profileId`，并保证所有持久化都以 `profileId` 为命名空间隔离

### 4.2 ProfileId 的确定方式

- 若 `DUEL_INSTANCE` 存在，则 `profileId = DUEL_INSTANCE`
- 否则 `profileId = "default"`

`DUEL_INSTANCE` 由调试多开脚本注入（A/B/...），因此调试双开天然获得两套隔离数据。

### 4.3 目录结构（建议）

以 `AppDataDir` 为根（平台相关的 app data 目录），每个 profile 拥有独立子目录：

- `profiles/<profileId>/settings.json`
- `profiles/<profileId>/saves/`
- `profiles/<profileId>/replays/`
- `profiles/<profileId>/cache/`

约束：

- `cache/` 必须可随时删除，不得放唯一数据
- `settings.json` 与 `saves/` 必须具备版本字段并支持迁移

### 4.4 写入策略（原子性）

所有关键文件写入必须满足：

- 使用临时文件写入完成后再原子替换（避免写到一半进程退出导致损坏）
- 不允许“读不到就随便 fallback 并写回”，必须走明确的迁移/默认值合并策略

设置系统的迁移与单一事实来源约束以 [设置系统设计.md](设置系统设计.md) 与仓库根目录 [AGENTS.md](../../AGENTS.md) 为准。

### 4.5 高频变更与写入节流（强约束）

立即生效模型下，部分设置项会产生高频变更（典型：滑杆拖动、连续调整数值）。为避免性能问题与磁盘写放大，必须遵守：

- Store 的内存态可以高频更新（保证观感与即时生效）
- 持久化必须由统一 persistence 层 debounce（例如 250ms）处理
- 禁止 UI 层自行决定落盘时机（避免不同页面行为不一致）

---

## 5. 单实例策略与调试多开的兼容

建议的产品/研发策略：

- 发布版：启用单实例（第二次启动时聚焦到已有实例）
- 调试多开：当 `DUEL_INSTANCE` 存在时禁用单实例限制，允许 A/B 多进程并行

这套策略与 Profile 隔离配合后，能保证：

- 玩家侧默认不出现“双开踩数据”的问题
- 研发侧可以稳定双开联调，且 A/B 的设置与存档互不影响
