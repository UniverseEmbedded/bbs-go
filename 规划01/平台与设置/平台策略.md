# 平台策略

现在模板用 Tauri 的好处是：桌面 + 移动打包链路你已经铺了（CI 也写了）。但你要的目标里 **"SteamVR + 安卓 VR"** 是最容易踩坑的一项，因为它不是"打包就行"，而是"运行时能力"的问题。

建议你把平台目标拆成两条线：

## A 线：Tauri（桌面/安卓/iOS）作为"主发行壳"

| 平台 | 注意事项 |
|------|----------|
| 桌面 | 性能 OK，输入也好做 |
| 安卓 | WebGL + three.js 可以，注意功耗与发热 |
| iOS | 要非常小心（WebGL2、内存、后台、WebXR）——建议先把 iOS 定义为"非 VR 版本"，至少第一阶段别把 VR 成败绑在 iOS 上 |

## B 线：VR 作为"支持 WebXR 的运行环境优先"

| 平台 | 策略 |
|------|------|
| SteamVR | 优先用 **浏览器 WebXR** 跑通（最小可行） |
| 安卓 VR | 如果是 Quest 系列，WebXR + three.js 反而更顺；如果是杂牌 Android VR 壳，能力差异会很大 |

## 结论

VR 能力别绑死在 Tauri 上，至少要保留"纯网页运行"的通路。

## Android：LAN 联机与明文 WebSocket（ws://）

LAN v1 客户端使用 `ws://`（明文 WebSocket）。Android 的 Debug/Release 对明文流量策略可能不同，常见现象是：

- Debug 包能连局域网
- Release 包连不上（看起来像“没权限/网络坏了”）

排查与约束：

1. Manifest 侧通常会使用 `android:usesCleartextTraffic` 控制明文流量是否允许
2. Tauri Android 模板里该值可能由 Gradle `manifestPlaceholders` 注入，Debug 与 Release 分别配置
3. 如果继续使用 `ws://`，Release 必须显式允许明文流量；否则需要升级到 `wss://` 并配证书（LAN 场景成本更高）

实现定位（便于维护）：
- `duel-app/src-tauri/gen/android/app/src/main/AndroidManifest.xml`：`android:usesCleartextTraffic`
- `duel-app/src-tauri/gen/android/app/build.gradle.kts`：`manifestPlaceholders["usesCleartextTraffic"]`
