# 库框架参考

本文档整理项目使用的库和框架的API定义、用法、生命周期、开发构建、测试策略、常见坑。

---

## Tauri v2

### API 定义与基本用法

**推荐用法（有 bundler）**：直接从 `@tauri-apps/api` 模块化导入各个命名空间（event/window/path 等）。

**Vanilla JS 备选**：可以用 `window.__TAURI__`，但需要开启 `app.withGlobalTauri` 配置；默认不是开箱可用。

### 权限/能力（Capabilities）是 v2 的关键

Tauri v2 用 capability/permission 体系替代 1.x 的 allowlist：

- **权限（permissions）**需要在 **能力（capabilities）**里引用后才会授予某个 window/webview
- capability 文件可放在 `src-tauri/capabilities` 下，JSON/TOML 都行；并可按平台（windows/macOS/linux/iOS/android）做差异化
- 一个窗口属于多个 capability 时，会合并权限边界（更容易"权限意外变大"），需要非常克制

### 生命周期要点

- **前端生命周期**：Tauri API 本质是前端调用后端命令/插件能力；"能不能用某个 API"取决于 capability 是否给了该窗口权限
- **配置生命周期**：只要你改了 capability/permission 配置，就相当于改了应用的安全边界——应当视为"需要审查"的变更

### 开发与构建注意事项

- capability 目录里"默认自动启用"的行为与"在 tauri.conf 明确启用后只启用那几个"的行为不同；团队应该统一成一种做法，否则经常出现"本地能用、打包不能用"
- 如果你需要允许远程 URL 访问某些 Tauri 命令，capability 里可以配置 `remote.urls`，但官方也提示在 Linux/Android 上 iframe 与窗口请求难区分，要非常谨慎

### 如何测试

- **别测官方 API 是否存在**（那是文档定义）；要测的是**你自己的能力边界**：
  - 单元测试：对"权限是否允许某个操作"的封装层做 mock/断言
  - E2E：只覆盖关键的"无权限时是否优雅失败、提示清晰"，而不是去验证系统级行为
- "能力/权限配置是否正确"更适合做一个 **CI 校验脚本**（静态检查 capability 文件是否包含你要求的权限集合），而不是跑一堆脆弱 UI 测试

### Store 插件（设置持久化）

说明：本节记录 Tauri store plugin 的通用用法与能力边界；但当前项目的设置持久化不以该插件为主路径，实际以“前端 SettingsStore + schema sanitize + Tauri settings_load/settings_save（或 Web localStorage）”落地为准。权威约束见：

- `规划01/平台与设置/设置系统设计.md`
- `规划01/平台与设置/调试多开与存档隔离.md`

**核心 API：**

- `const store = new Store('store.bin')`（JS 绑定时自动加载）
- `await store.set(key, value)` / `await store.get(key)`
- `await store.save()`（否则"正常退出时保存"）

插件命令默认被阻止，必须在 capabilities 里显式允许（例如 `store:allow-get`, `store:allow-set`, `store:allow-save`, `store:allow-load`）。

**生命周期要点：**

- Store 是"内存态 + 磁盘态"。你可以手动 `save()`，或者依赖正常退出保存
- JS API 参考里提到"销毁并从内存清理资源（destroy/cleanup）"，销毁后不应再调用

**是否需要新库：**建议引入 `zod`（或 `valibot`）做 Settings schema 校验与迁移输入验证。理由：Store 存的都是 JSON 值，长期维护必须要类型与迁移护栏。

### 事件系统

**核心 API：**

- `listen(eventName, handler)` 返回 `UnlistenFn`（组件卸载必须 unlisten）
- 内置事件枚举里包含 `WINDOW_THEME_CHANGED: "tauri://theme-changed"`

**用法建议：**

- 在 Shell/Adapter 层 `listen('tauri://theme-changed', ...)`，把结果派发到 SettingsStore（不要在 UI/渲染里到处 listen）
- Web 环境（非 Tauri）则用 `matchMedia('(prefers-color-scheme: dark)')` 做同样的 Adapter
  - 事件合并规则：系统主题变化只更新 system 探测态；不得覆盖用户显式的 `themeMode=light/dark`

### 系统托盘（TrayIcon + Menu）

**核心 API：**

- `TrayIcon.new(options)` 创建托盘图标
- `Menu.new({ items: [...] })` 创建菜单
- `menuOnLeftClick` 控制左键是否弹菜单
- `action` 回调能拿到 click/doubleclick/enter/move/leave 等事件

**生命周期要点：**

- TrayIcon 是"资源对象"，建议由 Shell 层创建/销毁；设置项变化只更新它的 menu/tooltip/icon，不要反复 new

### 通知（Notification 插件）

**核心 API：**

- `isPermissionGranted()` → `requestPermission()` → `sendNotification({title, body, ...})`
- `createChannel(...) / channels() / removeChannel(...)`（尤其 Android）
- `onAction(cb)` 监听用户对通知操作的交互；Actions 目前"仅移动端可用"

**平台坑：**

- Windows：通知"仅适用于已安装的应用"，开发态显示会比较怪
- 通道：无效 channelId 会导致通知不显示

## Vite

### API/配置定义（env/mode）

- dev 默认 `development` 模式，build 默认 `production`；可用 `--mode xxx` 加 staging 等自定义模式
- 只有 **以 `VITE_` 前缀**的变量会暴露给客户端代码（`import.meta.env.VITE_*`）
- 要获得 TS IntelliSense/限制未知 key，官方建议写 `vite-env.d.ts` 扩展 `ImportMetaEnv`

### 生命周期 & 开发要点

- `.env` 变更通常需要重启 dev server 才生效（这是常见"为什么我改了没反应"的根源）

### 如何测试

- Vite 本身不规定你用什么测试框架；常见做法是：
  - 单测：Vitest/Jest（取决于你配置）
  - E2E：Playwright/Cypress
- 你需要注意的是：**把"环境变量契约"当作规范**（AGENTS.md/架构文档写清楚哪些 env 必须存在、哪些不能在客户端暴露），测试只验证"缺失时有明确错误/降级"，别写"测试 env 加载顺序"这种重复造轮子

## three.js + WebXR

### API 定义与用法

- WebXR 在 three.js 里通过 `renderer.xr`（WebXRManager）管理；XR session 请求后会被注入 renderer，启动 XR 渲染
- 只要涉及 XR，推荐使用 `renderer.setAnimationLoop(fn)` 而不是自己写 `requestAnimationFrame`，因为它与 XR 帧同步机制集成更好（XR 刷新率/帧调度更正确）

### 生命周期

- **非 XR**：你可以 rAF 或 setAnimationLoop 都行
- **进入 XR**：必须 `renderer.xr.enabled = true`，并让渲染循环走 setAnimationLoop；退出 XR 后也要正确清理输入/事件监听（否则"退出后仍在触发 select"这类问题很常见）
- **能力探测**：不同容器/浏览器对 WebXR 支持差异巨大，单靠文档不够；因此你需要把"探测 + 回退逻辑"当作长期规则（写在规范里），而不是靠一次性原型记忆

### 如何测试

- 自动化测试很难覆盖真实 XR 会话；建议分层：
  - 单元测试：你自己的 XRAdapter 状态机（mock "支持/不支持""进入失败"等分支）
  - 手动/设备验证：只跑最小脚本（进入/退出/控制器 select）

### WebXR 参考空间

- WebXR 的参考空间是"只读的"，要改变视角/原点必须换一个 reference space
- MDN 明确说：要移动或旋转用户在世界中的视点，你需要改变使用的 `XRReferenceSpace`；但 reference space 是不可变的，所以要通过 `getOffsetReferenceSpace()` 创建一个新的空间来实现偏移/旋转
- three.js 的 `WebXRManager` 提供了 `setReferenceSpace()` 来覆盖默认参考空间，这正是实现"recenter"的钩子

## Troika Text

### API 定义与基本用法

- 核心是 `Text` mesh（来自 `troika-three-text`），用 SDF 生成字形 atlas；你设置 `text`, `font`, `fontSize` 等属性后渲染

### 生命周期（最重要的两个：sync / dispose）

- **sync**：属性改变后可以调用 `.sync()` 来立即触发排版/字形生成（否则也会异步 sync，但你拿不到"已就绪"的时点）
- **dispose**：不用的 Text 必须 `dispose()`，否则会泄漏 GPU/纹理/worker 相关资源（Troika README 明确强调 dispose）
- **字体预热/缓存**：预加载字体后会进入 texture atlas，后续实例用相同 font 路径可复用（减少首次卡顿）

### 开发与构建要点

- 字体文件（ttf/otf/woff）路径与打包后的资源路径要一致；如果你走 Vite + 资产 hash，建议统一封装一个 `resolveFontUrl()`，避免"开发能加载、打包 404"

### 如何测试

- 不要写测试去验证 Troika 的 SDF 算法正确（库自己保证）
- 要测的是你的使用规范：
  - 属性更新是否必调用 `sync`
  - 销毁路径是否必调用 `dispose`
  - 字体 URL 解析是否可在 dev/build 两端一致
- 这些都可以是单测（不需要真实 WebGL）

## i18next

### 核心 API

- `i18n.changeLanguage(lng)`：切语言；不传 `lng` 会走 language detector；还支持 `cimode`（测试用：t 总返回 key）
- React 侧用 `useTranslation()` 获取 `t` 和 `i18n` 实例；如果资源没 ready，可能触发 Suspense（可用 `useSuspense: false` 关闭）
- 初始化与 fallback：i18next 初始化文档强调 `fallbackLng` 默认会是 `'dev'`，你可以设置 `fallbackLng: false` 关闭 fallback 查找

### 生命周期要点

- 热切换语言 = `changeLanguage` + UI 自动重渲染（react-i18next 负责）
- 如果你做"按需加载翻译文件"，就要处理"切换语言时资源未加载完成"的状态（Suspense 或 loading）

### 开发与构建

- 资源文件建议按 namespace 拆分、支持延迟加载；Vite 下 `.json` 可直接 import，也可走 fetch（看你是否要动态增量更新语言包）

### 如何测试

- 单测：把语言设为 `cimode`，断言 UI 使用了正确 key（避免翻译文本变更导致用例频繁改）
- 另加 1～2 个 E2E：切语言后关键页面是否全部更新（含通知文案模板、设置页 label）

### 备选方案：FormatJS

如果你更关心 ICU message 复杂格式、编译提取与一致性流程，FormatJS 更强，但配套工具链更多。

## howler.js（音频）

### 核心 API

- 创建：`new Howl({ src: ['sound.webm', 'sound.mp3'], loop, volume, onend, ... })`
- 播放：`sound.play()`；事件：`sound.once('load', ...)` / `sound.on('end', ...)`
- 全局控制：`Howler.volume(0.5)`
- 大文件/流媒体：`html5: true` 强制 HTML5 Audio（避免等完整解码）

### 生命周期

- 音频对象数量会越来越多时，务必规划：
  - 常驻 BGM：复用一个 Howl（换曲目时 stop/unload 再建或切 src）
  - SFX：用 sprite 或对象池复用
- 移动端：Mobile Safari "after user input" 才可靠播放
- 浏览器自动播放限制：MDN 总结了媒体与 WebAudio 的 autoplay 策略，你要在"用户手势"后解锁/恢复 AudioContext 或开始播放

### 开发与构建

- 资源打包：建议把 BGM/SFX 放在固定 assets 路径，避免 hash URL 变化导致缓存/预加载逻辑混乱
- 多格式：Howler 建议提供多种格式（webm/mp3/wav）以提升兼容性

### 如何测试

- 单测：测你的 AudioSystem 的状态机（mute、分组音量、ducking 规则、切场景 stop/keep）；把 Howler mock 掉
- 手动：iOS/Android 真机解锁策略与后台/前台恢复（这类自动化不稳）

## 联机库

### 原生 WebSocket

**核心 API：**

- 构造：`new WebSocket(url[, protocols])`
- 事件：`onopen/onmessage/onclose/onerror`
- 方法：`send(data)` / `close(code, reason)`；close 的 code/reason 有规范限制（reason UTF-8 ≤ 123 字节等）

**生命周期：**

- 你需要自己处理：重连策略、心跳、房间/会话恢复、消息序列号与丢包重发（如果你需要可靠顺序）

**如何测试：**

- 单测：协议编解码、状态机、重连退避
- 集成测：启动一个本地 WS 服务器（node/ws），跑最小连接/断线/重连

### Socket.IO

**核心能力：**

- `emit()` 可带确认回调（ack），并且支持 `timeout(ms).emit(...)` 做超时处理
- `socket.volatile.emit(...)`：连接未准备好时直接丢弃（很像"只要最新位置"的 UDP 思路）

这对于"高频位置/输入"类消息很有用：你可以把"关键事件"走可靠 ack，把"瞬时状态"走 volatile。

### Colyseus（游戏房间框架）

**核心 API：**

- `new Client("http://localhost:2567")` 连接到服务器
- 提供房间、玩家加入离开、状态同步、消息路由

**你为什么可能需要它：**

- 如果你不想自己写"房间、玩家加入离开、状态同步、消息路由"，Colyseus 能少走很多弯路（尤其适合 Duel 房间战）

**如何测试：**

- 你可以在 CI 起一个 Colyseus server，跑 join/create、断线重连、状态更新订阅的冒烟用例

### 建议选型

- **第一阶段**：用原生 WebSocket + 你自己的协议（最少依赖），或直接上 Socket.IO（省重连/ack/volatile 设计成本）
- **如果你明确想要房间+状态同步且不想自研**：引入 Colyseus（更贴近游戏后端范式）

## 跨库共通注意事项

1. **Tauri 权限边界 ≠ 代码能不能跑**：优先靠 capability 配置审查/静态校验，而不是靠 UI 测试撞出来
2. **three.js XR 必须与渲染循环耦合**：XR 模式下渲染 loop 一定要走 setAnimationLoop，否则帧同步/输入事件会很怪
3. **Troika Text 资源生命周期必须明确**：`sync()`/`dispose()` 不写成规范，就会出现"偶发卡顿/内存涨"的鬼问题
4. **Vite env 合同要写清楚**：哪些 env 允许暴露、哪些必须 server-only（尤其未来如果加远端联机/配置）
5. **资源型对象必须有生命周期管理**：
   - Tauri `listen()` 必须 unlisten
   - Howler/Troika 这类对象要有 unload/dispose 策略
