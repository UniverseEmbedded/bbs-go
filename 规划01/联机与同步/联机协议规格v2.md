# 联机协议规格 v2（单 Server 多房间）

本文档定义“单个 Server 实例内可创建多个房间”的联机协议（protocol=2）。

v2 的目标是：在保持“权威服务器 tick + 客户端插值渲染”的前提下，引入房间目录（rooms）与房间识别码（roomCode），并规定“仅主机可创建/管理房间”。未来远程联机/账号系统可在本协议基础上扩展鉴权与更丰富房间元数据。

---

## 1. 目标与非目标

### 1.1 目标

- 单个 Server 实例支持多个房间（2 人对战）。
- 房间可选识别码（按房间独立），用于加入门槛与邀请分享。
- 仅主机连接可创建/关闭/重命名房间。
- mDNS 发现为主路径；发现粒度为“Server 实例入口”，不在发现阶段暴露房间列表。
- 同机多开支持范围：Level 3（多实例可发现/可开服/可加入；单 Server 多房间）。

### 1.2 非目标

- 远程联机、公网穿透、账号系统与权限系统（未来文档另述）。
- 观战、多人房间、跨房间聊天。
- 断线续局、自动重连（可作为后续版本演进）。

---

## 2. 术语

| 名称 | 说明 |
|------|------|
| Server | 一个 WebSocket 服务端实例（端内开服或独立服务）。 |
| Host | 运行 Server 的同机主机 UI，拥有管理权限（创建/关闭/重命名房间）。 |
| Guest | 普通连接方，无管理权限。 |
| Room | Server 内的一个对战房间，最多 2 个槽位（P1/P2）。 |
| RoomId | 房间内部唯一标识（不面向用户展示）。 |
| RoomCode | 房间识别码（面向用户展示与输入）。 |
| Slot | 房间槽位：p1 或 p2。 |

---

## 3. 编码与通用约定

### 3.1 编码

- 所有消息均为单条 UTF-8 JSON，单条 WebSocket frame 内完整包含一条 JSON。
- 未知字段必须忽略（便于协议扩展）。

### 3.2 版本协商

- 客户端在 `hello` 中声明 `protocol: 2`。
- 服务端在 `hello_ack` 中回 `protocol: 2`。
- 协议不匹配：服务端返回 `join_reject { reason: "bad_protocol" }` 或在 `hello` 阶段返回 `error` 并断开（实现可选，但需在服务端一致）。

### 3.3 时间与随机

- 服务端权威 tick，固定 TPS。
- 随机种子由服务端在进入房间（join_room_ack）时下发，用于房间内模拟确定性。

---

## 4. 权限模型（Host-only 管理）

### 4.1 HostToken

为满足“仅主机可创建/管理房间”，v2 定义 HostToken：

- Server 启动时生成随机 `hostToken`（不在 mDNS/UDP 广播中公开）。
- 同机主机 UI 通过平台通道获取该 token（例如 Tauri 事件或调用 `host_status` 取回）。
- Host 连接在 `hello` 中携带 `hostToken`，服务端验证后标记该连接为 `isHost=true`。

说明：

- HostToken 不是账号系统，只是 LAN 环境下的轻量管理钥匙。
- 服务端不得在日志中输出完整 token。

### 4.2 权限规则

- `create_room / close_room / rename_room`：仅 `isHost=true` 允许；否则返回 `error { code:"not_host" }`。
- 其它房间内操作（加入、输入、rematch）对 Host 与 Guest 一致。

---

## 5. 房间模型

### 5.1 RoomId 与 RoomCode

- `roomId`：字符串，建议 UUID v4；只在协议中使用，不要求用户可读。
- `roomCode`：三位数字字符串 `"000"`..`"999"`，按房间独立。
  - 若房间启用识别码，则加入时必须提供正确的 `roomCode`。
  - `roomCode` 在同一 Server 的“当前活跃房间”内必须唯一。

### 5.2 房间最小元数据（RoomSummary）

服务端对客户端公开的房间摘要信息：

```ts
type RoomSummary = {
  roomId: string;
  name: string;
  codeRequired: boolean;
  slots: {
    p1: { joined: boolean; name?: string };
    p2: { joined: boolean; name?: string };
  };
  state: "idle" | "playing" | "result";
};
```

规则：

- 房间列表中不公开 `roomCode` 本身（避免把识别码当作“公开密码”）。
- `state` 仅用于 UI 提示（是否进行中/已结算），不作为同步权威依据。

### 5.3 房间生命周期（建议）

- `idle`：等待玩家加入/准备。
- `playing`：对局进行中。
- `result`：结算阶段，等待 rematch 投票或返回房间。
- 房间关闭：仅 Host 可关闭；服务端可选支持空房间自动关闭（是否启用由服务器配置决定）。

  "client": {

{
  "t": "hello_ack",
  "protocol": 2,

  }

## 7. 消息：房间目录（Rooms）

### 7.1 list_rooms（C→S）

```json
{
  "t": "list_rooms"
}
```

### 7.2 rooms（S→C）

服务端返回当前完整房间列表：

```json
{
  "t": "rooms",
  "rooms": [
    {
      "roomId": "e5c1...",
      "name": "房间 1",
      "codeRequired": true,
      "slots": {
        "p1": { "joined": true, "name": "Alice" },
        "p2": { "joined": false }
      },
      "state": "idle"
    }
  ]
}
```

### 7.3 rooms_update（S→C）

服务端在房间目录变化时推送增量更新（可选，但推荐）：

```json
{
  "t": "rooms_update",
  "op": "upsert",
  "room": {
    "roomId": "e5c1...",
    "name": "房间 1",
    "codeRequired": true,
    "slots": { "p1": { "joined": false }, "p2": { "joined": false } },
    "state": "idle"
  }
}
```

```json
{
  "t": "rooms_update",
  "op": "remove",
  "roomId": "e5c1..."
}
```

## 8. 消息：房间管理（Host-only）

### 8.1 create_room（C→S，Host-only）

```json
{
  "t": "create_room",
  "name": "房间 1",
  "codeRequired": true,
  "roomCode": "123"
}
```

规则：

- `name` 可为空字符串，服务端可自动命名（如“房间 N”）。
- `codeRequired=false` 时忽略 `roomCode`。
- `roomCode` 缺省时，服务端生成一个未被占用的三位码。
- `roomCode` 冲突或格式错误：返回 `error { code:"bad_room_code" }` 或 `error { code:"room_code_taken" }`。

### 8.2 create_room_ack（S→C）

```json
{
  "t": "create_room_ack",
  "roomId": "e5c1...",
  "roomCode": "123"
}
```

说明：`roomCode` 只在创建确认里回给 Host，用于 UI 展示与邀请分享。

### 8.3 rename_room（C→S，Host-only）

```json
{
  "t": "rename_room",
  "roomId": "e5c1...",
  "name": "新房间名"
}
```

### 8.4 close_room（C→S，Host-only）

```json
{
  "t": "close_room",
  "roomId": "e5c1..."
}
```

服务端关闭房间时，若存在已加入的连接，需向该房间内所有连接发送 `room_closed` 并断开其房间会话。

### 8.5 room_closed（S→C）

```json
{
  "t": "room_closed",
  "roomId": "e5c1...",
  "reason": "closed_by_host"
}
```

## 9. 消息：加入/离开房间

### 9.1 join_room（C→S）

```json
{
  "t": "join_room",
  "roomId": "e5c1...",
  "as": "p1",
  "name": "玩家昵称",
  "roomCode": "123"
}
```

规则：

- `roomId` 必填（通过房间列表获得）。
- `as` 必填，值为 `"p1"` 或 `"p2"`。
- `name` 可选，服务端可用于 UI 展示。
- 该房间 `codeRequired=true` 时，`roomCode` 必填且必须匹配。
- 同一连接一次只能加入一个房间；若已在房间中，需先 `leave_room`。

### 9.2 join_room_ack（S→C）

```json
{
  "t": "join_room_ack",
  "roomId": "e5c1...",
  "you": "p1",
  "seed": 123456789,
  "tick": 0
}
```

### 9.3 join_room_reject（S→C）

```json
{
  "t": "join_room_reject",
  "roomId": "e5c1...",
  "reason": "bad_room_code",
  "retryAfterMs": 5000
}
```

`reason` 取值建议：

- `room_not_found`
- `room_full`
- `slot_taken`
- `bad_room_code`
- `rate_limited`

### 9.4 leave_room（C→S）

```json
{
  "t": "leave_room",
  "roomId": "e5c1..."
}
```

服务端应在离开后更新房间槽位，并触发 `rooms_update` 与 `room_state`（若仍有其它连接在房间内）。

## 10. 消息：房间内同步（Room-scoped）

v2 规定：所有房间内消息必须携带 `roomId`，用于 Server 内多房间路由。

### 10.1 room_state（S→C）

```json
{
  "t": "room_state",
  "roomId": "e5c1...",
  "tick": 120,
  "codeRequired": true,
  "slots": {
    "p1": { "joined": true, "name": "Alice" },
    "p2": { "joined": false }
  }
}
```

### 10.2 input_state（C→S）

```json
{
  "t": "input_state",
  "roomId": "e5c1...",
  "seq": 42,
  "input": {
    "moveX": 0.2,
    "moveY": -0.1,
    "aimX": 0.0,
    "shotPressed": true,
    "longShotPressed": false
  }
}
```

规则：

- `seq`：客户端单调递增的序号，服务端只保留 seq 最大的 input_state
- 缺输入策略：服务端复用 last_input；玩家断开连接时重置为默认值

### 10.3 snapshot（S→C）

```json
{
  "t": "snapshot",
  "roomId": "e5c1...",
  "tick": 240,
  "snapshot": {
    "tick": 240,
    "controlMode": "single",
    "arenaLayout": "vertical",
    "demoPlay": false,
    "showsInstructionWindow": false,
    "screenShakeValue": 0,
    "renderSuppressed": false,
    "gameState": { "kind": "play", "properFrameCount": 120 },
    "players": {
      "p1": { "kind": "move", "x": 320, "y": 540, "rotation": 0.5, "aimAngle": 1.57, "chargedFrameCount": 0, "damageRemainingFrameCount": 0, "fillColor": { "r": 255, "g": 255, "b": 255 } },
      "p2": { "kind": "move", "x": 320, "y": 100, "rotation": 0.3, "aimAngle": -1.57, "chargedFrameCount": 0, "damageRemainingFrameCount": 0, "fillColor": { "r": 0, "g": 0, "b": 0 } }
    },
    "arrows": { "p1": [], "p2": [] },
    "particles": []
  }
}
```

完整结构定义见第 13 节"核心数据结构"。

### 10.4 rematch_vote / rematch_state

```json
{
  "t": "rematch_vote",
  "roomId": "e5c1...",
  "want": true
}
```

```json
{
  "t": "rematch_state",
  "roomId": "e5c1...",
  "want": { "p1": true, "p2": false }
}
```

## 13. 核心数据结构

字段定义以 `duel-app/src/backend/types.ts`（`PlayerInput` / `BackendSnapshot` 等）与 `duel-app/src/net/protocol.ts` 为准；本文只描述传输语义与兼容规则。

### 13.1 PlayerInput

玩家输入帧，由客户端发送给服务端：

字段约束：

- `moveX/moveY`：`[-1, 1]` 移动方向输入
- `aimX`：`[-1, 1]` 蓄力阶段瞄准微调（角速度输入，非瞄准向量）
- `shotPressed/longShotPressed`：电平态（按住为 `true`）

**aimX 语义说明**：

- `aimX > 0`：`aimAngle` 以固定角速度递增（持续向一个方向旋转）
- `aimX < 0`：`aimAngle` 以固定角速度递减
- `aimX = 0`：`aimAngle` 不微调
- 仅在"蓄力/大招按住"阶段生效；非蓄力阶段即便 `aimX` 非 0 也不影响瞄准

### 13.2 BackendSnapshot

服务端下发的完整游戏状态快照：

字段定义见 `duel-app/src/backend/types.ts` 的 `BackendSnapshot`。

### 13.3 粒子同步策略

联机模式下，粒子属于表现层效果：客户端基于 `join_room_ack.seed` 与服务端快照序列本地重建。

**设计考量**：

- `snapshot.particles` 可为空/忽略（建议服务端置空以降低带宽）
- 客户端只依赖快照中的确定性状态（如玩家/箭矢/阶段）来生成观感一致的粒子
