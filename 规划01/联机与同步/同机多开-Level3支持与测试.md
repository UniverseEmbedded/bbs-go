# 同机多开（Level 3）支持与测试

本文档定义“同一台设备上同时运行多个客户端实例”的支持范围（Level 3）、设计约束与测试用例。

本项目对同机多开的目标：在 LAN 联机作为整体路线图的一部分时，确保多实例联调与开发/测试不会被端口/发现机制互斥所阻断。

---

## 1. 背景与动机

同机多开常见于：

- 开发联调：同机启动 2 个客户端快速验证加入、断线、弱网等行为。
- QA 测试：同机多窗口/分身模拟多人加入与房间管理流程。
- 桌面平台：用户双开（不作为主要用户场景，但不应崩溃或陷入假状态）。

---

## 2. 支持范围定义（Level 3）

### 2.1 Must（必须支持）

- 同机运行多个客户端实例时：
  - 每个实例都能进行服务器发现（以 mDNS 为主路径）。
  - 每个实例都能独立连接任意 Server 并加入房间。
- 同机运行多个“开服实例”（多个 Server）时：
  - 允许多个 Server 并行运行（端口不得固定，必须可自动分配）。
  - 每个 Server 在发现列表中可区分且可连接。
- 单个 Server 内支持多房间（protocol=2）：
  - 多实例客户端能连接同一 Server 并分别加入不同房间。

### 2.2 May（可选支持）

- UDP 广播发现作为加速或兼容回退，在平台允许端口复用时启用；若无法监听固定端口，应降级为“仅 mDNS”且 UI 给出诊断提示（不影响基本功能）。
- 同机实例过滤“发现到自己”：
  - 可选择显示（便于自连测试）或隐藏（更贴近真实 LAN 体验），需在 UI 上标识“本机服务器”。

### 2.3 Not support（明确不支持）

- 一个客户端连接同时加入多个房间（multi-join）作为常规功能。
- 一个房间超过 2 人或观战。
- 同机多开作为正式玩家玩法优化（例如自动分屏、键位冲突引导等）。

---

## 3. 关键设计约束

### 3.1 发现主路径：mDNS

同机多开下，UDP 固定端口监听经常出现互斥（多个进程无法同时 bind 同一端口）。为保证 Level 3 的 Must 条款成立：

- 发现必须以 mDNS browse 为主路径。
- mDNS 不可用时，必须提供“手动连接”兜底。
- UDP 广播发现只能作为可选能力，且不能成为“发现列表可用”的前置条件。

### 3.2 多开开服：端口分配与可区分性

- 端口不得固定（禁止默认永远 9001）。
- 开服流程必须返回“实际监听端口”与可连接地址，并用于：
  - mDNS SRV 端口
  - UI 展示（IP:端口）
  - 邀请分享
- 多个 Server 实例必须能区分：
  - mDNS 实例名包含短标识（如 hostIdPrefix 或端口后缀）。
  - UI 发现列表展示 `#短ID` 与 `IP:端口`。

### 3.3 “仅主机可建房”的鉴权

在同机多开下，不能依赖“本机只有一个客户端”来推断谁是主机；必须使用明确的能力标记：

- Server 启动生成 `hostToken`。
- Host UI 获取 token 并在 `hello` 时携带。
- 服务端对管理接口执行 `isHost` 校验，失败返回 `not_host`。

---

## 4. 发现与连接的降级策略（UI 必须可解释）

### 4.1 mDNS 不可用

表现：

- 发现列表为空或提示“扫描失败”。

要求：

- UI 显示明确提示：mDNS 不可用，请使用手动连接。
- 仍可通过手动输入地址连接并进入房间列表。

### 4.2 UDP 不可用（端口冲突/权限）

表现：

- UDP 发现不可用，但 mDNS 仍可用。

要求：

- 不影响发现列表基本可用性。
- UDP 的失败仅在“详情/诊断”中展示，不阻塞主流程。

## 5. 测试用例（Level 3）

### 5.1 同机双开客户端：发现与加入

前置：

- 同一台设备启动客户端实例 A 与 B。
- 同一 LAN 内存在一个 Server（可为同机或他机）。

步骤：

1. A 打开联机面板，确认能看到服务器列表（mDNS）。
2. B 打开联机面板，确认也能看到相同服务器列表。
3. A 进入某 Server，加入房间 1 为 P1（必要时输入识别码）。
4. B 进入同一 Server，加入同一房间 1 为 P2。

通过标准：

- 两个实例均可完成发现与加入。
- 任一实例断开不会导致另一实例 UI 假死或状态错误（应显示对手离线/占槽变化）。

### 5.2 同机双开开服：并行 Server 可用

前置：

- 同一台设备启动客户端实例 A 与 B。

步骤：

1. A 在“开服”页启动服务器，记录其端口与短ID。
2. B 也启动服务器，确认端口不同且短ID不同。
3. A/B 的“加入房间”页都能在列表里看到两个 Server，且可区分。
4. A 连接到 B 的 Server，加入其房间；B 连接到 A 的 Server，加入其房间（交叉验证）。

通过标准：

- 两个 Server 可并行运行且可连接。
- UI 无“看似开服成功但实际不可连接”的假状态。

### 5.3 同机多实例连接同一 Server：多房间

前置：

- 有一个 Server（可同机或他机），已创建至少 2 个房间（Host-only）。

步骤：

1. 实例 A 加入房间 1（P1）。
2. 实例 B 加入房间 2（P1 或 P2）。
3. 检查两实例的 Net HUD 与房间状态互不串扰。

通过标准：

- 房间内消息按 roomId 路由正确，不出现“串房间”的 snapshot/input。

## 6. 观测与排错建议（开发/测试）

- 在联机面板/详情中可展示：
  - serverName、#短ID、IP:端口
  - mDNS/UDP 可用性（仅诊断）
- 在 Debug 面板可展示：
  - 当前 roomId、网络状态机状态
  - RTT、丢包/乱序统计、插值缓冲深度
- 调试同机双开（Tauri 多进程）与数据隔离策略见 [调试多开与存档隔离.md](../平台与设置/调试多开与存档隔离.md)
