# 自动化测试策略

## 设计原则

把每个模块拆成 **Core（可测）** + **Adapter（难测）** + **E2E（可半自动）** 三层，然后针对不同层用不同测试手段。

---

## 哪些测试可以不做（改为 AGENTS.md 约束）

**凡是"框架/库本身已经稳定定义的行为"，我们不需要再写一套测试去验证它"是不是按文档工作"**；更好的做法是——把"我们依赖它的前提、版本范围、用法约束、已知坑与替代方案"写进架构设计 + AGENTS.md，让后续实现和评审都按这些前提推进。

### 1) 构建/启动命令、工具链约束（Vite/TS/Tauri）

- **不需要测试**"Vite dev/build 能不能跑""TypeScript 能不能编译"这种事；它们是工具链的定义行为
- 应该做的是：在 AGENTS.md 固化 *唯一正确命令* 和 *版本边界*，比如 `pnpm install` / `pnpm dev` / `pnpm build`、node/pnpm 版本、是否必须锁依赖等；并把 `tsc` 作为**静态检查门槛**而不是测试

**结论：**"工具链是否正常"靠文档 + CI 运行命令即可，不必写额外测试用例。

### 2) Tauri JS API 的"接口存在性/调用方式"

比如你会用到 `@tauri-apps/api` 里的模块化导入方式（event/window/path 等），这些在官方文档里写得很明确。你不需要写测试去证明"import 能用""模块名存在"。相反，把**你允许用哪些 API、禁用哪些能力、权限最小化策略**写清楚更重要。

**结论：**验证"API 按文档存在/可导入"没意义；把"允许调用的边界"写进 AGENTS/架构即可。

### 3) 纯"概念性架构边界"本身（不涉及运行时差异）

例如架构设计里要求把系统拆成 Core Simulation / Input / Presentation / Shell，并明确 Core **不引用 three.js/DOM/WebAudio**。这种东西的正确性更多靠**代码组织 + lint 规则 + 依赖约束**来保证（比如 core 包不允许依赖 three.js），而不是写测试。

**结论：**"层次分离"用工程约束落实，比做测试更直接。

### 4) "已知无法在 CI 稳定自动化"的 OS 行为

Tauri 真窗体 resize 在 CI 难稳定自动化，跨 OS/窗口管理器坑多。这类东西如果你硬塞到自动化测试里，最后只会变成**随机红**。更合适的做法是：

- 在 AGENTS.md 写：CI 不测真窗体 resize；只测浏览器 viewport resize（或只测你自己的"响应逻辑"）
- 用"可注入事件源"方案（ThemeSource/WindowMetricsSource 等）

**结论：**凡是"CI 里不稳定/不可控"的 OS 行为，不要写成自动化测试目标，写成**手动验证清单 + 可注入模拟**更靠谱。

## 最容易被自动化测试覆盖的部分（优先写单元/属性测试）

### 1) 生命周期与事件钩子的"事件总线/状态机"

**为什么好测**：纯逻辑；输入是事件序列；输出是状态与订阅回调顺序。

**建议测试**：

- 事件顺序：`ready -> windowCreated -> resized -> themeChanged...`
- 去抖/节流逻辑：resize 高频触发时只产生预期次数的 `layoutUpdate`
- 订阅/取消订阅：不会泄漏、不会重复触发
- "覆盖优先级"：系统主题变化 vs 用户手动覆盖的优先级规则

**测试类型**：单元测试 + 属性测试（随机事件序列）

**覆盖率潜力**：很高（70–90% 逻辑都能测）

---

### 2) i18n：locale store + 文本选择/格式化规则

**为什么好测**：输入（locale、key、params）→输出（string）。

**建议测试**：

- key 缺失 fallback
- ICU/复数规则（如果你用 i18next/lingui）
- 动态切换不会遗留旧语言（store 正确更新）
- 长文本策略（wrap/ellipsis）可以通过测"测量策略选择"而不是像素

**测试类型**：单元测试（快）

**覆盖率潜力**：很高

---

### 3) 网络延迟注入器（jitter/loss/reorder）

**为什么好测**：这是典型"可模拟时钟 + 队列"的模型。

**建议测试**：

- 给定随机种子时输出确定（可重现）
- 丢包率/乱序率统计接近配置
- RTT/jitter 统计计算正确
- 重传/ack 逻辑（如果你做）正确

**测试类型**：单元测试 + 属性测试（Monte Carlo）

**覆盖率潜力**：非常高（几乎全自动）

---

### 4) 性能压力台的"配置矩阵/采样统计"

**为什么好测**：统计部分是纯逻辑。

**建议测试**：

- P50/P95、滑动窗口平均、异常值裁剪
- 采样间隔与时间戳处理
- Profile 切换正确影响"预期的渲染参数集合"（开关映射表）

**测试类型**：单元测试

**覆盖率潜力**：中高（渲染本身不测，统计全测）

---

### 5) 音频混音的"路由与电平策略"（不含真实播放）

**为什么好测**：你可以把 WebAudio 节点当成接口 mock，测试 gain automation 的计划。

**建议测试**：

- bus 结构：BGM/SFX/UI/Voice 的连接图正确
- ducking 规则：UI/Voice 触发时 BGM gain 曲线（attack/release）被正确调度
- 并发限制：SFX 同类同时最多 N 个，超出策略（丢弃/替换/叠加衰减）

**测试类型**：单元测试（用 fake audio graph）

**覆盖率潜力**：中高（播放时延与设备差异不测）

---

## 可以"半自动 / E2E 自动化"的部分（但别指望 100% 稳）

这些通常需要 **Playwright/Cypress** 跑 UI，然后通过截图/日志断言。对你这种跨平台壳来说，Web 端 E2E 最稳；Tauri 端 E2E 难度会上一个台阶，但你至少能让同一套前端在浏览器里跑通大部分。

### 6) 深色模式、i18n、页面路由、设置持久化

**可测点**：

- 切换主题后 DOM class/css var 改变
- three scene 的 theme token 变化（暴露 debug 面板：当前主题值）
- locale 切换后关键 UI 文本更新
- 刷新/重启后设置从存储恢复（浏览器可测；Tauri 侧可能要 mock storage）

**工具**：Playwright（推荐）

**风险**：跨 OS 的系统主题事件难以在 CI 稳定触发 → 可以用"手动模拟系统事件"的 debug command 代替真实系统事件（可测性设计很重要）

---

### 7) 窗口 resize（浏览器里可测，桌面壳里不稳定）

**可测点**：

- canvas 尺寸与 camera aspect 更新
- 输入坐标映射正确（点击屏幕角落应该选到正确 UI）

**工具**：Playwright 在浏览器里做 viewport resize 很稳

**Tauri 真窗体 resize**：CI 很难稳定自动化（不同 OS/窗口管理器坑很多）

---

### 7.1 输入方向语义回归清单（必须覆盖）

这类问题的特点是：构建能过、功能也能跑，但“左右反了”会直接破坏可玩性；并且经常出现“一端对、一端错”。因此需要把方向语义固定成清单，改动任何输入/透视/布局相关代码都必须跑一遍。

最低覆盖矩阵（手动或半自动均可）：

| 场景 | 操作 | 期望现象 |
|------|------|----------|
| 桌面：LAN 作为 P2 | 蓄力阶段（按住大招）持续做“向左/向右”微调 | 瞄准应按输入方向旋转（不出现左右反向） |
| 移动：LAN 作为 P2 | 同上（触控/摇杆水平输入） | 同上 |
| 移动：本地双人竖屏 P2 | 蓄力阶段持续做“向左/向右”微调 | 在 P2 对坐视角中，瞄准应与其左右输入一致 |
| 移动：单人竖屏 | 左摇杆向左/向右移动 | 角色移动方向与摇杆一致，且不影响右侧按钮命中 |

推荐把“如何观察瞄准旋转”写进验收脚本（例如：录屏对比/按键提示/可视化辅助），避免只靠主观手感。

## 最可能必须人工测试的部分（或只能做"很薄的自动化"）

### 8) VR（WebXR）

**原因**：CI 环境基本拿不到真实 XR runtime、控制器、帧率/合成器行为。

**能自动化的薄层**：

- WebXR capability 探测逻辑（`isSessionSupported` 的分支）可以单测/mock
- "XR 模式状态机"可以单测

**必须人工**：

- 进入/退出 XR session 的真实行为
- 控制器射线/手柄映射
- VR 帧率与眩晕相关的体验问题

> 结论：VR 需要"手动测试脚本 + 录屏/日志采集"，自动化只能覆盖 20% 左右。

---

### 9) 中文字体"观感与清晰度"

**原因**：像素级渲染受 OS 字体渲染器、DPR、GPU、浏览器实现影响太大。

**能自动化的薄层**：

- 字体加载成功/失败 fallback（能自动测）
- 生成 N 个 Troika Text 不报错（能自动测）

**必须人工**：

- "糊不糊""边缘发虚""字号在 VR 里可读性"
- 不同设备上的实际呈现

---

### 10) 低端设备的真实性能极限

**原因**：桌面 CI 或模拟器跑出来的指标对真实低端机参考价值有限。

**能自动化的薄层**：

- 性能采样代码正确（前面说了）
- 在浏览器里跑 smoke perf test（只能当回归，不能当绝对值）

**必须人工**：

- 真机（尤其安卓低端、iOS 老机）测发热、降频、掉帧形态

---

### 11) 系统托盘/系统通知（跨 OS）

**原因**：权限、系统策略、聚焦行为、通知中心差异。

**能自动化的薄层**：

- 触发通知的逻辑、payload 构造（单测）
- 前端收到"通知点击"事件后的路由行为（E2E）

**必须人工**：

- 通知是否真正弹出
- 点击后窗口是否前置（不同 OS 限制不同）
- 托盘菜单在不同系统主题下的表现

---

### 12) 音频真实播放与混音"听感/延迟"

**原因**：浏览器 autoplay 策略、设备输出缓冲、蓝牙延迟、系统音量混音策略。

**能自动化的薄层**：

- 你的混音路由策略（前面说了）

**必须人工**：

- "打爆"时是否破音
- 延迟是否可接受
- 移动端解锁音频流程是否顺畅

---

## 关键建议：为可测试性设计

很多"本来必须手测"的内容，如果你把系统事件都抽象成 **可注入的虚拟事件源**，自动化覆盖能显著提高：

- `ThemeSource`: `system` + `manualOverride`，并提供 `debugEmitThemeChange()`
- `WindowMetricsSource`: 在浏览器里用 viewport 模拟，在桌面壳里用真实事件
- `NotificationAdapter`: 真实发通知 vs 测试时记录到内存队列
- `XRAdapter`: 真实 WebXR vs mock session（至少能测状态机与 UI）

这样 CI 跑的不是"真实 OS 行为"，而是"你的代码对事件的响应"——这才是最可控的。

## 账号系统（E阶段）专项：最可能失败点优先

账号系统与 Bot API 的测试目标是“契约一致 + 幂等安全 + 状态机正确”，重点不是 UI。

- 专项清单见：[账号系统自动化测试清单.md](../账号与运营/账号系统自动化测试清单.md)
- 最小验收测试包建议优先跑：Bot HMAC 固定向量、nonce+request_id 幂等、Outbox pull/ack 并发一致性、门禁状态机、邀请 token 兑换规则

---

## E4远程联机（EasyTier / 远程当 LAN）专项

E4 的自动化测试重点不是“节点是否可用”，而是把我们自己的控制面、UI 降级口径、可分享地址与日志导出链路固定成可回归的契约。

- 专项设计见：[E4远程联机（EasyTier）自动化测试设计.md](E4远程联机（EasyTier）自动化测试设计.md)

## 结论表（按你关心点）

| 分类 | 内容 |
|------|------|
| **不需要测试（改为 AGENTS.md 约束）** | 工具链可用性、API 存在性、层次分离正确性、CI 不稳定的 OS 行为 |
| **最值得优先写单元测试** | 事件总线/状态机、i18n、延迟注入器、性能统计、音频混音策略 |
| **最适合 Playwright 做 E2E** | 主题切换（用模拟事件）、locale 切换、设置持久化、浏览器 viewport resize、UI 回归 |
| **最可能必须人工** | VR 全流程、中文字体观感、低端机真实性能、托盘/系统通知跨 OS、音频听感/延迟 |
