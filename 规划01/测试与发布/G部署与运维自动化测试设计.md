# G部署与运维自动化测试设计

本文档为里程碑 G“部署与运维”提供可回归的自动化测试设计。目标是保证：容器化/编排/自动化部署/备份恢复/监控输出 的关键契约稳定，并避免把公网、证书签发、真实云资源波动等不可控因素引入 CI 失败源。

## 范围与边界

### 目标（要自动化覆盖）

- G1 容器化：镜像能构建、服务能最小启动、基础健康检查可用
- G2 Compose 编排：一键启动/关停幂等，依赖关系与端口暴露正确
- G3 frp：隧道链路“可连通”与配置回归（不追求公网质量）
- G4 Ansible：语法与幂等性基础保障，关键文件/目录/权限的契约稳定
- G6 备份：备份文件可用、可恢复，且（若启用）加密/解密链路可用
- G5 监控：监控输出格式稳定、可解析；阈值判断逻辑稳定（数据驱动决策不漂移）

### 非目标（不做自动化断言）

- Let’s Encrypt 真签发/频率限制/公网 80/443 可达性
- 真实云服务器资源读数的准确性（只测“解析与决策逻辑”）
- 真实公网链路的延迟、抖动、断连概率（只测“连通性最小闭环”）
- 真实 QQ/NapCat 行为与登录链路（不纳入 G 的自动化核心）

## 分层测试设计（Lint / Contract / Integration / E2E）

### 1) Lint（静态检查）

- Dockerfile：基础 lint（可选），至少保证 build stage/复制路径不缺失
- docker-compose.yml：语法校验与引用文件存在性校验
- Ansible：`--syntax-check` 与变量必填校验（缺变量应明确失败）
- Shell 脚本：基础 shellcheck（可选），至少保证错误可见

产出：在“未接触真实环境”的情况下尽早失败，降低部署时才发现错误的概率。

### 2) Contract（契约测试，纯逻辑/纯文本输出）

适用于：monitor.sh、备份脚本的参数解析、阈值判断逻辑、输出格式等。

必须覆盖：
- 监控输出包含固定字段（时间戳、CPU、内存、磁盘、DB 大小等），单位与字段名稳定
- 阈值判断：输入假数据时能稳定产出对应“建议升级动作”（不依赖真实机器）

### 3) Integration（单机集成，使用容器与本地网络）

适用于：Go 服务端 / duel-server / frp 的最小闭环、备份恢复闭环。

原则：
- 全部在本地 docker network 内完成
- 不依赖外网服务、第三方节点、真实域名

### 4) E2E（可选：自托管 Runner / 本地演练脚本）

- 覆盖更贴近真实的链路：例如 frps+frpc 的端到端、备份落本地设备路径、定时任务（cron）安装
- 允许不在公共 CI 跑，但必须可重复运行，并产出标准化日志/结果

## 用例矩阵（按里程碑 G1~G6 对齐）

### G1：容器化

- G1-T1（build）：Go 服务端镜像可构建
- G1-T2（build）：duel-server 镜像可构建
- G1-T3（build）：Koishi 镜像可构建（或验证 Dockerfile 可用）
- G1-T4（smoke）：Go 容器启动后最小 API 可达（不要求对外 HTTPS）
- G1-T5（smoke）：duel-server 容器启动后 WebSocket 端口可连接（握手成功即可）

断言要点：
- 退出码为 0（build）
- 进程不立即崩溃（smoke）
- 端口监听/基础请求可达（smoke）

### G2：Docker Compose 编排

- G2-T1（up/down 幂等）：`up -> down -> up` 不需要人工清理卷/网络即可再次成功启动
- G2-T2（依赖与互访）：Go 容器能按 service name 访问 duel-server（如设计需要）
- G2-T3（暴露正确）：对外暴露的端口集合符合预期（不多暴露管理端口）

断言要点：
- 所有服务进入“运行态”（可用 healthcheck 则用 healthcheck）
- 日志中无重复创建导致的错误（例如端口占用/卷权限错误）

### G3：frp 内网穿透

- G3-T1（最小连通）：启动 frps + frpc + 一个 echo 服务，断言从 frps 暴露端口能访问到 echo 服务
- G3-T2（配置回归）：关键配置项变更能在测试中体现（例如端口、token、映射名）

断言要点：
- 连接建立成功
- 请求可往返（HTTP 200 或 TCP 回显一致）

### G4：Ansible 编排

- G4-T1（syntax）：playbook/role 语法检查通过
- G4-T2（idempotent 基础）：对同一目标执行两次不会出现“第二次必然失败”的任务
- G4-T3（关键产物）：部署后关键文件落位（compose、环境文件占位、备份脚本、定时任务等）

说明：
- 若暂不引入 VM/容器目标机，可先把 G4-T2/T3 作为“自托管 Runner/本地演练脚本”执行项。

### G5：监控与决策系统

- G5-T1（格式契约）：monitor 输出为固定结构（建议 JSONL 或 TSV；若先用纯文本也要固定字段）
- G5-T2（阈值逻辑）：喂入假数据覆盖所有阈值分支，断言产出的“升级建议”稳定

断言要点：
- 字段齐全、单位稳定、可解析
- 阈值边界（等于/大于）行为固定

### G6：备份方案（核心）

- G6-T1（备份可用）：在运行态 SQLite 上执行 `.backup` 得到备份文件；备份文件可打开并可通过完整性检查（如启用）
- G6-T2（恢复闭环）：向原库写入可识别数据 -> 备份 -> 用备份库查询/启动恢复环境 -> 数据存在且一致
- G6-T3（加密链路，可选）：备份文件加密后可解密；解密产物可通过 G6-T2

断言要点：
- 恢复出来的数据一致
- 失败时错误清晰（路径/权限/口令缺失）

## 执行策略（避免不稳定源）

建议拆两条跑法：
- 公共 CI 必跑：Lint + Contract + 本地 Integration（不触网、不签证书、不用真实云资源）
- 自托管/本地演练：包含更贴近公网与真实落机的验证（frp/Ansible/cron/权限/磁盘空间等）

---

## 日志与敏感信息规则

- 测试日志不得打印：JWT 密钥、OAuth client secret、HMAC key、备份加密口令
- 任何测试用的 `.env`/密钥仅由运行环境注入，不进入仓库
- 失败信息要可定位：明确是构建失败/端口不可达/恢复校验失败/解析失败等类别

---

## 最小交付（建议里程碑内先做到的程度）

- 必做：G1 build+smoke、G2 up/down 幂等、G6 恢复闭环、G5 输出契约
- 可后置：G3 的公网质量相关、G4 的真实落机演练（但至少保留 syntax-check）
