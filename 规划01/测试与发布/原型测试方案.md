# 原型测试方案

## 开发流程调整说明

**原型测试甚至不需要着急做，p5.js也不要着急换。**

目前第一步是把后端给分离出来（然后加上联机功能，或者至少加上本地双人的功能），重点在分离前后端。分离了之后就可以开始写API文档了，然后再做原型，再做本体。

### 调整理由

- **把高耦合风险前置化解**：先分离core，后面换渲染（p5→three）或加VR都只是"表现层替换"，风险显著降低
- **文档可以更早产出并更稳定**：API文档基于core契约，比基于UI/渲染更不容易反复改
- **联机/双人是结构验证器**：它逼你把"输入→模拟→输出"的闭环做到干净

### 与原规划的关系

| 原规划 | 调整后 |
|--------|--------|
| 先做原型测试 | 先分离前后端 |
| 原型后再写API | 分离后立即写API |
| 原型验证后再做联机 | 本地双人在分离阶段就做 |

**核心变化：**把"分离Core"从"架构设计里的原则"变成"第一个必须完成的里程碑"。

详细的里程碑规划请参考 [开发流程里程碑.md](开发流程里程碑.md)。

## 设计原则

目标是：**每个原型都比"完整游戏"小一截，但能尽早暴露你方案的硬风险**。

把原型设计成 **一个"实验台（Lab）应用" + 多个可独立开关的 micro-spike**，每个 spike 都满足：

- **可在 1 个晚上内做完**（最好 1–3 小时有结论）
- **通过/失败都能立即产出决策**（继续用 Tauri？换壳？换字体策略？VR 只能走浏览器？）
- **复用到主项目**（代码直接变成框架层的模块，而不是扔掉）

## 总体结构：一个 Lab，所有测试都挂在同一套生命周期钩子上

Lab 只做一件事：提供一个统一的 `AppLifecycle` 与 `EventBus`，然后每个 spike 是一个"插件"：

- `onAppReady`
- `onWindowCreated`
- `onWindowResized`
- `onThemeChanged`（系统深色模式变化）
- `onLocaleChanged`（运行时切换 i18n）
- `onTrayAction`
- `onNotification`
- `onXRSessionStart/End`
- `onNetworkStats`
- `onPerfSample`
- `onAudioDeviceChanged`

这样你不是"先做游戏再补钩子"，而是**先把钩子做成能被所有 spike 验证的骨架**。

## 4 个核心原型配额

在只有 4 个独立原型配额的前提下，优先押在**"会直接决定路线/架构边界"的硬风险**上。

### A1：窗口生命周期与 Resize 稳定性（桌面壳）

**为什么占一个配额**：这是壳层"地基"，你后面所有 UI/渲染/输入坐标映射都会被它影响。

**目标**：窗口可自由调整大小时，你的渲染循环/布局/输入坐标不会崩。

**最小内容**：

- 一个 three.js canvas + 一个 DOM UI overlay
- resize 时：更新 renderer size、camera aspect、UI 布局断点
- 记录 resize 事件频率（有些平台会疯狂触发）

**严格边界（不扩圈）**：只做 resize 引发的三件事：renderer size、camera aspect、overlay layout；不做主题/i18n/托盘/通知。

**通过标准**：

- 连续拖拽 30 秒不闪烁、不拉伸、不掉输入
- resize 过程中帧率不跌到"卡死"（比如 <10fps 持续）

**产出决策**：你需要节流/防抖策略、以及"渲染与布局分离"是否必须。

---

### A2：深色模式动态切换（系统跟随 + 手动覆盖）

**为什么占一个配额**：它直接验证"系统事件 → store → three scene & Troika/DOM"的数据流是否通顺，并且能暴露 Troika Text 更新策略（重建 vs 更新）的卡顿/闪烁风险。

**目标**：系统主题变化/手动切换时，UI + three 场景 + Troika 文本都能无缝更新。

**最小内容**：

- UI 用 CSS variables（`--bg`, `--fg`, `--accent`）
- three 场景也从同一套 theme token 取色（材质参数/雾/背景）
- 提供 3 个模式：Follow System / Light / Dark

**严格边界**：只做 theme token 与渲染联动（CSS variables + three 从同一套 token 取色）；不把 i18n、设置持久化、路由一起塞进来。

**通过标准**：

- 系统主题切换后 200ms 内全量更新
- Troika Text 不出现"先黑后白"或字体重建卡顿

**产出决策**：theme token 的数据流到底从哪儿来（系统→store→渲染），以及 Troika Text 更新策略（重建 vs 更新材质）。

---

### B1：中文字体渲染策略对比（Troika vs DOM）

**为什么占一个配额**：这是"中文项目成败点"，而且会决定 UI 走 DOM 还是 Troika、字体打包是否需要子集化/按需加载。

**目标**：中文显示清晰、性能可控、包体可控。

**最小内容**：

- 同一段中文/中英混排/emoji，分别用：
  1. DOM（CSS）
  2. Troika Text（3D/overlay）
- 场景里生成 200 个名字牌（中文昵称）做压力测试
- 动态更新其中 50 个文本（模拟血量/倒计时）

**严格边界**：只测"文本清晰度 + 文本相关的性能"；不把阴影/后处理/粒子等通用性能项扩进来（那些是 E1 的事）。

**通过标准**：

- 名字牌 200 个仍能保持目标帧率（桌面 60、移动尽量 45+）
- 中文不"糊成一团"，不同 DPR 下可读

**产出决策**：

- UI 文本尽量 DOM、场景内才 Troika
- 字体打包策略：subset（子集化）是否必须、以及 fallback 选择

---

### C1：WebXR 能力探针 + 最小 XR Session 闭环

**为什么占一个配额**：它是 VR 路线的"生死探针"，因为真正不确定的不是 three.js，而是"你选的容器/运行环境是否支持 WebXR"，并且平台策略明确要求 VR 至少要保留纯网页通路。

**目标**：你选的"运行环境组合"里，VR 到底能不能跑。

**最小内容**：

- 一个网页模式入口（同一代码在浏览器跑）
- `isSessionSupported('immersive-vr')` 探测并显示原因
- 进入 XR 后：双手柄射线点选一个按钮、播放一声 click

**严格边界**：只做 `isSessionSupported` + 进入/退出 XR + 手柄射线点按钮 + 播放 click；不做 VR UI 体系、不做性能档位、不做联网。

**通过标准**：

- 至少在一个目标设备闭环成功（例如：SteamVR 浏览器环境 或 Quest 浏览器）
- XR 进入/退出不崩，重复 3 次

**产出决策**：VR 是否必须走"纯网页运行"作为官方路径；Tauri 里 VR 是否先放弃。

## 其他原型（本轮不做）+ 不做理由

> 这里的"不做"，不是说永远不要，而是：在你只有 4 个独立配额的前提下，它们要么**可由架构/AGENTS.md 先约束掉风险**，要么**依赖前面 4 个结论才能有效推进**，要么**属于可后置的产品增强**。

### A3：i18n 动态切换（中英切换 + 复数/格式化）

**本轮不做理由：**

- 其中"字体 fallback/中文切换"很大一部分会被 **B1** 的字体结论覆盖（否则你会在 i18n 原型里重复踩字体坑）
- i18n 选型（i18next/lingui/小字典）更适合先写进架构与 AGENTS.md：**键命名规范、fallback 规则、禁止在 core 里直接拼字符串**等先约束起来，等 UI 框架稳定后再做原型更划算

### A4：托盘图标 + 系统通知（Windows/macOS）

**本轮不做理由：**

- 这是明显的"壳层增强"，对你的核心风险（VR 路线、中文文本、渲染/UI 架构边界）不如前四者"决定性"
- 而且它很依赖"你最终是否继续押 Tauri 作为主壳"的决策；这个决策在 **A1/C1** 做完后更清晰，再做不迟

### D1：延迟注入器（Latency/Packet loss/Jitter）

**本轮不做理由：**

- 它属于"纯逻辑可测"的模块，适合直接走 **单元测试/属性测试**（而不是用掉一个"原型配额"）。自动化测试策略里也明确它"非常好测、覆盖率潜力高"
- 并且它的价值在你确定联机模型（锁步/回滚）后更大；当前阶段优先把"壳/VR/文本"硬风险先压下来更划算

### E1：性能压力台（fill-rate / draw calls / text / postprocess 分项开关）

**本轮不做理由：**

- 你现在优先级里，"文本性能/可读性"已经由 **B1** 覆盖了一块；而其它项（阴影/后处理/粒子/光源）在你确定了 A1 的渲染/布局边界、以及 C1 的 VR 路线之前，测出来也很可能要重做
- 更现实的顺序是：先用 B1 确定"文本占比与策略"，再用 E1 做"整体渲染预算"

### F1：音频引擎 spike（WebAudio：同时发声/混音/ducking/延迟）

**本轮不做理由：**

- 这条确实容易翻车，但它对"路线选择"的决定性不如 C1/B1；而且很多"路由与电平策略"可先做成可测试的纯逻辑（fake audio graph），把原型配额留给更依赖真实运行时能力的风险点
- 等你确定了平台路径（尤其 iOS/安卓的壳策略）后，再做音频原型更有效，因为移动端音频限制差异会影响结论

---

## 并行落地建议

把这 4 个原型分成 3 条并行泳道：

1. **Shell Lane**：A1 窗口 Resize + A2 深色模式
2. **Render Lane**：B1 中文字体对比
3. **Tech Risk Lane**：C1 WebXR 探针

每条泳道的代码都挂到同一个 Lab app 的侧边栏里，点一下就进入某个测试页。你和 AI 每次只盯一个页签，不会被"主线大工程"吞噬。

---

## 完成这 4 个后的决策点

做完这四个，你基本就知道：

- Tauri 这条路值不值得继续
- VR 是否必须分叉（纯网页运行）
- 中文字体怎么落
- 渲染/UI 的架构边界该怎么定
