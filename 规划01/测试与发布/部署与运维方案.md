# 部署与运维方案

本文档定义几何决斗项目的部署与运维方案，包括容器化设计、编排方案、备份策略和监控决策系统。

运行手册与排障见：[`运维Runbook（故障与操作手册）.md`](运维Runbook（故障与操作手册）.md)

---

## 1. 概述

### 1.1 背景

当前项目已完成账号系统（E1-E3），进入部署与运维阶段。本文档定义如何将服务部署到云服务器，并建立数据驱动的运维决策机制。

### 1.2 资源现状

| 资源 | 配置 | 用途 |
|------|------|------|
| 日本 VPS | 2C2G + 40G，500G上行/月，500M带宽 | 公网入口、游戏对局服务、核心 API |
| 本地设备 | 112G 内存 + 4T 存储 | Koishi 机器人、备份存储 |
| 家庭宽带 | 100M | 本地设备联网 |

### 1.3 部署架构

```
                    ┌─────────────────────────────────┐
                    │         日本 VPS                  │
                    │  ┌─────────────────────────┐    │
                    │  │ Go 服务端 + SQLite      │    │
                    │  │ Rust duel-server        │    │
                    │  │ frp server             │    │
                    │  └─────────────────────────┘    │
                    └──────────────┬──────────────────┘
                                   │
                              frp tunnel
                                   │
                    ┌──────────────┴──────────────────┐
                    │         本地设备                  │
                    │  ┌─────────────────────────┐    │
                    │  │ Koishi + NapCat         │    │
                    │  │ 备份存储 (4T)           │    │
                    │  │ frp client             │    │
                    │  └─────────────────────────┘    │
                    └─────────────────────────────────┘
```

## 2. 容器化设计

### 2.1 Go 服务端容器化

#### 构建策略

采用多阶段构建策略，分为构建阶段和运行阶段。

**构建阶段**

使用官方 Go 镜像作为构建环境。核心任务是下载依赖并编译二进制文件。基础镜像选择 `golang:1.24-alpine`，因为 Alpine 镜像体积小，且项目使用的 `modernc.org/sqlite` 是纯 Go 实现，不需要 CGO，可以静态链接。

**运行阶段**

使用 Alpine Linux 作为运行环境，只包含编译好的二进制文件、CA 证书和时区数据。最终镜像体积约 20-30MB。

#### 数据持久化设计

Go 服务端运行时需要持久化三类数据。

**数据库文件**

SQLite 数据库文件必须持久化。使用数据卷挂载方式，容器内定义挂载点，运行时映射到宿主机目录。

**SSL 证书缓存**

Let's Encrypt 证书有有效期和申请频率限制，证书缓存必须持久化，同样通过卷挂载解决。

**静态网站文件**

有两种方案。方案 A 是打包进镜像，优点是部署简单，缺点是更新网站需要重新构建镜像。方案 B 是挂载宿主机目录，优点是更新网站只需替换文件，缺点是多一个挂载点。建议选择方案 B，因为项目官网更新频率较高。

补充说明：

- 当前仓库的 Dockerfile 仍包含 “将 web_dist 打包进镜像” 的兜底路径，但实际部署编排会通过 volume 将宿主机的 `server/web_dist` 挂载进容器，从而实现“更新网站仅替换构建产物即可生效”。

#### 配置管理设计

敏感信息使用环境变量注入，包括 JWT 密钥、OAuth 客户端密钥、机器人认证密钥等。非敏感配置可以直接使用环境变量覆盖，Go 服务端代码已经支持此功能。

#### 网络与端口设计

Go 服务端需要暴露 80 端口（HTTP 流量，用于 Let's Encrypt ACME 挑战和重定向）和 443 端口（HTTPS 流量，主要服务入口）。容器内可以直接监听 80 和 443，宿主机端口直接映射。Go 服务端已内置 Let's Encrypt 证书管理，不需要额外的反向代理层。

### 2.2 Rust duel-server 容器化

#### 构建策略

同样采用多阶段构建。

**依赖管理复杂性**

duel-server 依赖 duel-core 库，两者在同一个 Cargo workspace 中。构建时需要复制整个 workspace 的 Cargo 配置和源码。

**静态链接**

Rust 可以静态链接 musl libc，生成完全独立的二进制文件。运行阶段不需要任何系统库，镜像可以基于极简的 Alpine。

#### 运行时设计

duel-server 是一个简单的 WebSocket 服务端，监听一个端口（默认 9001），不需要持久化存储，也不需要配置文件（通过命令行参数配置）。

#### 与 Go 服务端的关系

两个服务端独立部署。客户端先连接 Go 服务端获取房间信息，然后直接连接 Rust duel-server 进行游戏。在 Docker 网络中，它们在同一个网络中，可以通过容器名互相访问。

### 2.3 Koishi 容器化

#### 现有 Dockerfile 分析

项目已有 Koishi 的 Dockerfile，基于官方 Node.js Alpine 镜像，预装 Chromium 浏览器和中文字体，将 `/koishi` 目录定义为数据卷。

#### 改进方向

配置文件和插件已经存在于 `koishi/` 目录中。敏感信息（机器人密钥）用环境变量注入，数据持久化通过宿主机目录挂载。

#### 与 NapCat 的网络关系

NapCat 是 QQ 协议的实现，Koishi 通过 OneBot 协议与 NapCat 通信。在 Docker 环境中，两者应该在同一个 Docker 网络中。NapCat 使用官方镜像即可。

## 3. Docker Compose 编排

### 3.1 云服务端编排

#### 设计思路

服务端组件（Go 服务端 + Rust duel-server）部署在云服务器上，用一个 docker-compose.yml 统一管理。

#### 网络设计

两个服务在同一个 Docker 网络中，可以互相访问（为未来扩展预留），外部只能访问暴露的端口。

#### 卷管理

数据卷统一放在 `./data/` 目录下，便于备份和管理。Go 服务端的 SQLite 数据库和 SSL 证书缓存分别挂载。

#### 环境变量管理

敏感信息通过 `.env` 文件管理，docker-compose.yml 引用这些变量。`.env` 文件不提交到 Git。

#### 重启策略

使用 `unless-stopped` 策略，容器异常退出时自动重启，除非手动停止。

### 3.2 本地 Koishi 编排

#### 分离部署的原因

Koishi 需要连接 QQ（通过 NapCat），这需要本地有 QQ 客户端登录。部署在云服务器上会使 QQ 登录变得复杂（需要远程桌面或扫码），所以部署在本地更方便。

#### 网络设计

Koishi 和 NapCat 在同一个 Docker 网络中。Koishi 通过 Docker 内部网络连接 NapCat 的 OneBot API。

#### 与远程服务端的通信

Koishi 通过 HTTPS 连接远程 Go 服务端，使用 HMAC 签名认证。这部分不需要 Docker 网络配置，走的是公网。

### 3.3 frp 内网穿透设计

#### 部署架构

frp 分为 server（云服务器）和 client（本地设备）两部分。

**frp server**

部署在云服务器上，监听一个端口（默认 7000），等待客户端连接。配置简单，只需一个配置文件和启动命令。

**frp client**

部署在本地设备上，配置需要暴露的服务（如 Koishi 管理后台），通过 frp server 映射到公网端口。

#### 适合通过 frp 暴露的服务

Koishi 的管理后台、备份下载接口、开发调试用的临时服务。

#### 不适合通过 frp 暴露的服务

游戏对局（duel-server）和高频 API 调用，因为会增加延迟。

## 4. Ansible 编排

### 4.1 定位与价值

Ansible 的核心价值是"基础设施即代码"。把服务器配置、部署步骤写成可版本控制的剧本。

对于当前场景的价值包括：记录服务器配置便于重建、部署步骤可重复可审计、定时任务统一管理。

### 4.2 角色划分

#### docker 角色

负责安装 Docker 和 Docker Compose。包括添加 Docker 官方软件源、安装 docker-ce 和 docker-compose-plugin、配置 Docker 守护进程、将部署用户加入 docker 组。

#### duel-server 角色

负责部署游戏服务端。包括创建应用目录结构、复制 docker-compose.yml 和环境变量文件、启动服务、配置防火墙规则。

#### backup 角色

负责备份任务。包括安装备份脚本、配置 cron 定时任务、配置远程备份目标。

### 4.3 Playbook 设计

#### setup.yml

在新服务器上执行，完成基础配置。任务包括安装 Docker、创建用户和目录、配置防火墙。

#### deploy.yml

在代码更新后执行。任务包括同步配置文件、拉取新镜像、滚动更新服务。

#### backup.yml

配置备份任务。任务包括部署备份脚本、设置定时任务、测试备份恢复。

### 4.4 与 Docker 的协作

Ansible 和 Docker 是互补关系。Docker 解决应用如何运行，Ansible 解决应用部署到哪里和如何配置。Ansible 负责安装 Docker、创建目录、复制配置文件，Docker 负责运行容器。Ansible 可以通过 docker_compose 模块管理容器生命周期。

## 5. 数据库备份方案

### 5.1 SQLite 备份的特殊性

SQLite 是文件数据库，备份方式与 PostgreSQL/MySQL 不同。直接复制 `.db` 文件可能有问题，如果复制时有写入操作，复制的文件可能损坏。

正确的备份方式是使用 SQLite 内置的 `.backup` 命令。这是原子操作，不会产生损坏的备份，不阻塞读写操作，备份文件是完整的、可用的数据库。

### 5.2 备份脚本设计

备份脚本的核心逻辑包括：生成带时间戳的备份文件名、执行 SQLite backup 命令、压缩备份文件（可选）、上传到本地备份目录、清理过期的本地备份。

### 5.3 备份保留策略

| 备份类型 | 频率 | 保留时间 | 存储位置 |
|---------|------|---------|---------|
| 小时备份 | 每小时 | 24 小时 | 本地 |
| 日备份 | 每天 | 7 天 | 本地 |
| 周备份 | 每周 | 4 周 | 本地 |
| 月备份 | 每月 | 12 月 | 本地（4T 空间充足） |

### 5.4 备份到本地

本地有 4T 存储空间，备份直接存放在本地设备即可。不需要额外的云存储成本。

### 5.5 备份加密

数据库包含用户信息，备份应该加密。使用 GPG 对称加密，密码存储在安全的地方。加密时机是备份完成后本地保存之前。

## 6. 监控与决策系统

### 6.1 监控指标

#### 云服务器监控

| 指标 | 说明 | 触发条件 |
|------|------|---------|
| 内存使用率 | 2G 是否够用 | 持续 > 85% |
| CPU 使用率 | 2 核是否够用 | 持续 > 80% |
| SQLite 数据库大小 | 存储是否够用 | > 30G（留 10G 余量） |

#### 网络监控

| 指标 | 说明 | 触发条件 |
|------|------|---------|
| frp 延迟 | frp tunnel 的延迟 | 持续 > 50ms |
| frp 连接失败率 | frp 断连次数 | 每天断连 > 3 次 |
| 云服务器上行流量 | 月流量使用 | > 400G/月 |

### 6.2 监控方案

最简单的方式是一个 shell 脚本，定时记录内存、CPU、磁盘使用率和数据库大小，写入日志文件。frp 自带的 dashboard 可以看到连接数、流量和延迟。

### 6.3 数据驱动的升级路径

```
├── 内存 > 85%？
│   └── 是 → 数据库搬到本地，通过 frp 连接
│
├── 上行带宽跑满（> 400G/月）？
│   └── 是 → 静态资源走 CDN 或搬本地，升级宽带
│
├── frp 延迟 > 30ms 或频繁断连？
│   └── 是 → 申请公网 IPv4
│
└── 数据库 > 30G？
    └── 是 → 考虑清理数据或扩展存储
```

## 7. 实施步骤

### 7.1 阶段 1：基础部署

| 任务 | 产出 |
|------|------|
| 创建 Go 服务端 Dockerfile | server/go/Dockerfile |
| 创建 Rust duel-server Dockerfile | duel-app/src-tauri/Dockerfile.duel-server |
| 创建云服务端 docker-compose.yml | deploy/docker-compose.cloud.yml |
| 创建 frp server 配置 | deploy/frps/ |

**验收标准**：Go 服务端和 Rust duel-server 可以在 Docker 中正常运行。

### 7.2 阶段 2：本地部署

| 任务 | 产出 |
|------|------|
| 优化 Koishi Dockerfile | koishi/docker/Dockerfile |
| 创建本地 docker-compose.yml | deploy/docker-compose.local.yml |
| 配置 frp client | deploy/frpc/ |

**验收标准**：Koishi 可以通过 frp 与云端 Go 服务端通信。

### 7.3 阶段 3：自动化

| 任务 | 产出 |
|------|------|
| 创建 Ansible 角色和 Playbook | ansible/ |
| 创建备份脚本 | scripts/backup.sh |
| 创建监控脚本 | scripts/monitor.sh |

**验收标准**：ansible-playbook 可以完成服务器初始化，备份脚本可以定时执行。

### 7.4 阶段 4：监控与决策

| 任务 | 产出 |
|------|------|
| 完善监控脚本 | 定期输出资源使用报告 |
| 定义触发条件 | 明确升级决策阈值 |
| 建立数据记录 | 记录历史数据供分析 |

**验收标准**：可以根据监控数据做出升级决策。
