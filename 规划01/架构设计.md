# 架构设计

## 现有模板的优点与隐患

你现在的 `duel.ts` 是典型"单文件大循环 + Actor 类层级"的结构：输入→玩家引擎（Local/AI）→物理更新→渲染全揉在一起。这个结构做 p5 草图很爽，但一旦你要：

- 多人联机（需要确定性、可回滚/可重放）
- 道具/皮肤（数据驱动、资源管理）
- VR（渲染管线、相机/控制器输入、帧率保障）

它会开始"牵一发而动全身"。

## 四层架构切割方式

把系统拆成 4 个边界清晰的层（这一步比"换 three.js"更关键）：

术语澄清：本文件的“四层架构”是技术分层（后端/输入/前端/平台壳）。规划13中的“三层架构”是玩法分层（天文层/工厂层/决头层），两者是正交关系，不互相替代，详见规划13 [三层架构设计.md](../规划13/基础设计/三层架构设计.md)。

### 1. 后端（玩法/判定/AI/物理）

- 只做：状态、碰撞、伤害、技能/道具、AI决策
- **不引用 three.js / DOM / WebAudio / p5**
- 固定 60 TPS，可重放（输入日志驱动）
- 数值表示：TS 为 number，Rust 为 f64（不做额外量化）
- AI属于后端，但联机时走玩家接口（不下发AI内部状态）

### 2. Input（输入归一化）

- 键鼠/触屏双摇杆/手柄/VR 控制器 → 统一成 `InputFrame`
- 你现在已经有 `InputSnapshot` 了，这是优势：继续把它"升级成每 tick 的输入帧"，并让它可序列化（用于联机/回放）
- 输入语义：电平（down）+ 边沿（pressed/released）都提供
- 长按/蓄力由后端按tick计数累积
- 长弓瞄准：使用独立字段 `aimX` 调整 aimAngle，避免与移动 `moveX` 绑定造成的映射歧义

本地双人（双通道输入、键盘/触控映射、P2视角与UI倒置）详见 [本地双人设计.md](./输入与本地双人/本地双人设计.md)。

### 3. 前端（渲染/UI/粒子）

- three.js 场景图：Mesh、材质、粒子、相机、后处理
- Troika Text：UI 文字（血量、提示、房间号、对战结果）
- 粒子/屏幕抖动/尾迹等特效由“本地粒子系统”负责：
  - 单机：由后端直接生成并输出到 snapshot
  - 联机：服务端不下发粒子，客户端按 seed + 快照序列本地重建，观感与单机一致
- 注意：UI 建议走 **2D overlay（CSS/Canvas）+ 少量 3D Text** 的混合模式；VR 里再把关键 UI 投到 world-space

### 4. Platform Shell（壳）

- Tauri/浏览器/SteamVR：窗口、存储、网络权限、更新、手柄/VR 能力检测

这样你未来想把"壳"从 Tauri 换成 Electron 或纯浏览器 WebXR，也不至于把游戏逻辑重写。

## 后端与前端的边界

### 后端职责

| 职责 | 说明 |
|------|------|
| 状态管理 | BackendState（纯数据、可序列化） |
| 物理更新 | 位置/速度积分、碰撞检测 |
| 判定结算 | 命中/伤害/回合/胜负 |
| AI决策 | 产出PlayerInput，内部状态不下发 |
| 量化 | 步末统一×512/÷512 |

### 前端职责

| 职责 | 说明 |
|------|------|
| 渲染 | 读取BackendSnapshot，绘制场景 |
| 粒子特效 | 允许随机，不同步 |
| 音效 | 基于状态变化或事件触发 |
| UI | 菜单/设置/帮助等 |

### 接口契约

以实际代码类型为准：

- 后端输入/输出类型：`duel-app/src/backend/types.ts`
- 联机消息与快照封包：`duel-app/src/net/protocol.ts` 与 [联机协议规格v2.md](./联机与同步/联机协议规格v2.md)

## 驱动模式设计

### LocalDriver（单机/本地双人）

现有逻辑不变：
- 读InputSnapshot → backend.step → renderer.render

### NetDriver（联机）

详细设计见 [联机系统设计.md](./联机与同步/联机系统设计.md)。
当前实现以独立权威服务端（duel-server）为准：

- 服务端：tick loop + 复用最后输入态 + 广播快照
- 客户端：插值渲染快照 + 本地重建粒子（不做粒子网络同步）

## Rust后端架构

### duel-core（核心库）

- types.rs：类型定义（与TS对齐）
- rng.rs：随机数生成器
- backend.rs：DuelBackend核心逻辑
- math.rs：数学工具函数
- particles.rs：粒子系统
- ai.rs：AI决策

### duel-server（CLI服务端）

- protocol.rs：WS消息定义
- server.rs：tick loop + 连接管理
- net.rs：WS工具函数
- args.rs：CLI参数

## three.js + VR 的关键点

- VR 这块你基本会走 **WebXR**（three.js 自带 WebXRManager）。
- 真正的不确定性在于：**你选的容器是否支持 WebXR**。移动端 Safari/WebView、iOS 的 WKWebView、Windows WebView2 对 WebXR/手柄能力支持差异很大。

所以建议你把 VR 模式做成"可选运行时"：**同一套 build，在支持 WebXR 的环境启用 VR；不支持就退回普通 3D**。

- SteamVR 这边通常是用支持 WebXR 的 Chromium（比如 Chrome）跑，或者你自己打包一个 Chromium 壳；Tauri 的 WebView 路径反而可能更绕。
