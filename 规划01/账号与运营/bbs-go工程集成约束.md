# bbs-go 工程集成约束

本文档记录 bbs-go 作为第三方社区系统接入本仓库时的工程约束与维护策略，避免“前端源码移除”导致的协作与升级失控。

---

## 1. 引入方式（强约束）

- bbs-go 以 git submodule 引入，落点固定为 `server/bbs-go/`。
- 禁止把 bbs-go 以“复制源码/粘贴目录”的方式 vendoring 进仓库。
- 默认浅克隆（depth=40）以降低体积；但必须允许随时 deepen/unshallow，以保证关键历史提交可达。

### 1.1 必须可达的基线提交（用于前端维护）

- 以 `fe26ad02` 作为“前端源码仍存在”的基线点，用于对照新版后端变更并回填到自维护前端。
- 以 `01cb26a7` 作为“新版后端能力基线”，用于任务/投票/配置下发等能力对齐。

---

## 2. 变更策略（强约束）

- 所有与 bbs-go 相关的改动在 `main02` 分支进行。
- 不做 `git merge`；只允许“搬运内容（cherry-pick / 手动搬文件）→创建新修订”。
- 每次搬运都必须写明来源范围（例如：来源 commit、搬运的目录/文件清单、非目标）。

---

## 3. 前端源码移除应对（工程主路径）

### 3.1 已知事实

- bbs-go 新版中，`admin/` 与 `site/` 可能仅保留静态产物（`admin/assets/*`、`site/_nuxt/*`），不提供可构建源码工程。

### 3.2 主路径（必须遵循）

- 主路径：以“后端 git diff 驱动”为准，逐项将必要的能力与字段变更回填到自维护的前端源码（以 `fe26ad02` 为起点）。
- 产物 diff（对比压缩 JS/CSS）仅用于查漏：确认新前端是否覆盖某能力、是否出现某 API path/字段名；禁止作为主要开发路径。

---

## 4. 认证与账号体系（已定）

- 不接入 bbs-go 自带登录体系（注册/短信/微信/Google 登录均不作为接入路径）。
- 统一由本项目 Go 服务端登录并签发 JWT；bbs-go 仅做 JWT→本地用户映射/幂等创建/建立会话（如需要）。

---

## 5. 静态资源策略（已定）

- 采用 bbs-go 新版 `/res` 静态资源挂载（`res/images/...` 等由 bbs-go 服务端公开）。

---

## 6. 配置下发必须适配项

以下字段由 bbs-go 后端通过 `/api/config/configs` 下发，前端自维护时必须消费或至少兼容（不崩）：

- `baseURL`：用于绝对链接生成与运营配置的一致性。
- `scriptInjections`：用于 `<head>` 脚本注入能力（统计/埋点等）。
