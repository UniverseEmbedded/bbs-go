# Loomio 设计分析

> 【需要详细讨论】

本文档从设计层面解读 Loomio 的业务逻辑和设计哲学，为社区平台设计提供指导。

---

## 一、Loomio 是什么？

Loomio 是一个**协作决策平台**。它的核心目标是：

> 让一群人能够在一起做决定，而不需要开无休止的会议。

### 1.1 传统决策方式的问题

| 方式 | 问题 |
|------|------|
| 开会 | 效率低，需要所有人同时在线 |
| 邮件讨论 | 难以追踪，决策过程不透明 |
| 传统投票 | 只有"同意/反对"，无法表达复杂意见 |

### 1.2 Loomio 的解决方案

| 方案 | 解决的问题 |
|------|------------|
| 异步讨论 | 不需要同时在线 |
| 结构化投票 | 不只是简单多数 |
| 过程可追溯 | 所有讨论和投票都有记录 |

---

## 二、核心概念

### 2.1 群组（Group）

**问题：** 一群人要一起做决策，首先需要一个"容器"来组织这些人。

**解决方案：** 群组就是人的集合。

```
群组
├── 成员（Membership）
├── 管理员（admin: true）
└── 讨论列表（Discussion）
```

**设计要点：**

1. **权限分层** — 管理员可以管理成员、设置权限；普通成员只能参与讨论和投票
2. **可见性控制** — 群组可以是公开的（任何人可见）或私有的（仅成员可见）
3. **子群组** — 大组织可以有层级结构（例如：公司 → 部门 → 小组）

**为什么需要群组？**

没有群组，每次发起讨论都要手动选择谁能参与。有了群组，"谁能参与"就自动由群组成员关系决定了。

---

### 2.2 讨论（Discussion）

**问题：** 决策前需要讨论，但讨论容易跑题、难以追踪。

**解决方案：** 讨论是一个有结构的对话容器。

```
讨论
├── 标题
├── 内容描述
├── 评论列表
├── 投票列表
└── 时间线（Event）
```

**设计要点：**

1. **评论嵌套** — 可以回复帖子，也可以回复别人的评论
2. **时间线** — 所有事件（发帖、评论、投票、关闭）按时间排列
3. **状态管理** — 讨论可以关闭、重开

**为什么讨论和投票是分离的？**

一个讨论可能包含多个投票。例如：
- 讨论："我们下个季度应该做什么？"
- 投票1："优先级排序"
- 投票2："预算分配方案"

讨论是上下文，投票是决策动作。

---

### 2.3 投票（Poll）

**问题：** 传统投票只有"同意/反对"，无法表达复杂意见。

**解决方案：** Loomio 设计了多种投票类型。

**为什么需要多种投票类型？**

不同场景需要不同的决策方式：

| 场景 | 适合的投票类型 |
|------|----------------|
| "这个提案通过吗？" | 提案投票（四象限） |
| "会议时间选哪个？" | 会议投票（时间选择） |
| "预算怎么分配？" | 点数投票（分配点数） |
| "候选人排名？" | 排名投票 |

---

## 三、四象限投票的设计哲学

### 3.1 传统投票的问题

传统投票通常只有"同意/反对"两个选项：

```
同意 ────── 反对
```

问题：
1. **无法表达"我不确定"** — 弃权者被迫选边站
2. **无法表达"我有保留意见"** — 同意但需要修改
3. **无法表达"我强烈反对"** — 反对和"我坚决阻止"是一样的

### 3.2 四象限投票的设计

Loomio 的提案投票有四个选项：

```
        同意
         ↑
         │
弃权 ←───┼─── 需要修改
         │
         ↓
        阻止
```

**每个选项的含义：**

| 选项 | 含义 | 隐含态度 |
|------|------|----------|
| 同意 | 我支持这个提案 | "可以做" |
| 需要修改 | 我不完全同意，但愿意继续讨论 | "可以改" |
| 弃权 | 我不参与决策，接受任何结果 | "无所谓" |
| 阻止 | 我强烈反对，提案不应通过 | "不能做" |

### 3.3 为什么这样设计？

**核心理念：共识决策**

传统投票是"少数服从多数"，但这种方式有问题：
- 49% 的人反对，提案照样通过
- 反对者可能强烈不满，导致执行困难

共识决策的目标是：
> 让所有人都能接受结果，即使不是最优选择。

四象限投票如何支持共识决策：

1. **"需要修改"选项** — 表达"我愿意继续讨论"，而不是直接反对
2. **"阻止"选项** — 给强烈反对者一个明确的表达方式，但使用门槛高（不应滥用）
3. **"弃权"选项** — 让不关心的人不干扰决策

### 3.4 结果解读

| 投票结果 | 解读 |
|----------|------|
| 大多数同意，少数需要修改 | 通过，但需要关注修改意见 |
| 有人阻止 | 需要重新讨论，解决阻止者的顾虑 |
| 大量弃权 | 可能提案不够重要，或者信息不足 |

## 四、事件驱动架构

### 4.1 什么是事件？

**问题：** 用户做了很多操作（发帖、评论、投票），如何记录和通知？

**解决方案：** 每个操作都是一个"事件"。

```
事件（Event）
├── 类型（kind）：new_comment, poll_created, stance_created...
├── 触发者：谁做的
├── 主体：操作的是什么
├── 时间
└── 父事件：回复的是哪个事件
```

### 4.2 为什么用事件驱动？

**好处1：统一的时间线**

所有操作都是事件，可以按时间排列成一条时间线：

```
[讨论创建] → [评论A] → [投票发起] → [评论B] → [投票] → [投票关闭] → [结果声明]
```

**好处2：解耦通知**

当事件发生时，系统自动触发通知：
- 给关注者发邮件
- 给被提及者发通知
- 给 Chatbot 发消息

这些通知逻辑不需要写在业务代码里，而是通过事件订阅实现。

**好处3：审计日志**

所有事件都有记录，可以追溯"谁在什么时候做了什么"。

### 4.3 事件的嵌套设计

评论可以回复评论，形成树状结构：

```
事件1：帖子
├── 事件2：评论A（parent = 事件1）
│   ├── 事件3：回复A1（parent = 事件2）
│   └── 事件4：回复A2（parent = 事件2）
└── 事件5：评论B（parent = 事件1）
```

这样设计的好处：
- 可以展开/折叠回复
- 可以计算"回复数"
- 可以定位"这是对谁的回复"

## 五、权限系统设计

### 5.1 为什么需要权限系统？

不是所有人都能做所有事：
- 普通成员不能删除群组
- 非成员不能看到私有群组的讨论
- 投票关闭后不能再投票

### 5.2 权限的组成

权限 = 主体 + 动作 + 对象

```
"用户A" 可以 "关闭" "投票B"
```

### 5.3 权限的判断逻辑

Loomio 使用 CanCanCan 库，权限判断是**基于规则**的：

```
用户可以关闭投票，当且仅当：
- 投票正在进行中
- 且用户是投票管理员
```

### 5.4 权限的继承

权限可以从群组继承：

```
群组管理员
    ↓
可以管理群组内的所有讨论和投票

群组成员
    ↓
可以参与群组内的所有讨论和投票
```

### 5.5 为什么用模块化设计？

Loomio 有 20+ 个权限模块：

```
Ability::Poll      # 投票相关权限
Ability::Group     # 群组相关权限
Ability::Comment   # 评论相关权限
...
```

**好处：**
- 每个模块只关心自己的权限逻辑
- 新增功能时，只需新增模块
- 修改权限时，不会影响其他模块

## 六、立场模型（Stance）

### 6.1 什么是立场？

**问题：** 用户投票时，不只是选择一个选项，还可能要说明理由。

**解决方案：** 立场 = 选项 + 理由

```
立场（Stance）
├── 投票者
├── 所属投票
├── 选择的选项
└── 理由
```

### 6.2 为什么叫"立场"而不是"投票"？

"投票"暗示只是一个动作，但"立场"包含更多信息：
- 我选了什么
- 为什么这么选
- 我的态度是什么

### 6.3 立场可以修改

用户可以改变主意：
- 第一次：选择"需要修改"，理由是"预算太高"
- 第二次：选择"同意"，理由是"预算已调整"

系统保留所有历史记录，但只计算最新的立场。

---

## 七、结果声明（Outcome）

### 7.1 什么是结果声明？

**问题：** 投票结束后，如何总结决策结果？

**解决方案：** 结果声明是管理员对投票结果的官方解读。

```
结果声明（Outcome）
├── 声明内容："根据投票结果，我们决定..."
├── 关联的选项：选择哪个选项作为最终决定
└── 附件：相关文档
```

### 7.2 为什么需要结果声明？

投票结果不总是"非黑即白"：
- 40% 同意，30% 需要修改，20% 弃权，10% 阻止
- 如何解读这个结果？

结果声明让管理员可以：
- 明确最终决定
- 解释为什么这样决定
- 记录后续行动

---

## 八、设计原则总结

| 原则 | 体现 |
|------|------|
| **共识优先** | 四象限投票，而非简单多数 |
| **过程透明** | 所有事件可追溯 |
| **异步协作** | 不需要同时在线 |
| **权限清晰** | 谁能做什么，规则明确 |
| **结构化讨论** | 讨论和投票分离，避免混乱 |
| **可修改** | 立场可以改变，投票可以重开 |

---

## 九、核心思想

这套设计的核心思想是：

> **决策不是一次性动作，而是一个过程。**

Loomio 的所有设计都在支持这个过程：

```
讨论 → 投票 → 修改 → 再讨论 → 最终决定
```

而不是：

```
投票 → 结束
```

## 十、对我们的启示

### 10.1 投票功能设计

1. **支持多种投票类型** — 不同场景需要不同投票方式
2. **四象限投票** — 支持共识决策，而非简单多数
3. **立场可修改** — 允许用户改变主意
4. **结果声明** — 管理员可以解读投票结果

### 10.2 架构设计

1. **事件驱动** — 所有操作都是事件，支持时间线和通知
2. **权限模块化** — 每个功能模块管理自己的权限
3. **Concern 复用** — 可复用的能力模块

### 10.3 用户体验

1. **异步协作** — 不需要所有人同时在线
2. **过程透明** — 所有讨论和投票都有记录
3. **结构化** — 讨论和投票分离，避免混乱
