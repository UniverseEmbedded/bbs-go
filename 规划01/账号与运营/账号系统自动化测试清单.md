# 账号系统（E阶段）自动化测试清单

本文档把里程碑 E1–E3 的“最可能失败点”转成可执行的自动化测试清单，用于约束实现与评审范围。

关联文档：

- 里程碑定义：[`开发流程里程碑.md`](../总览与路线/开发流程里程碑.md)
- 服务端模块/接口设计：[`Go 服务端集成方案.md`](./Go服务端集成方案.md)
- Bot API / 门禁 / Outbox 契约：[`Koishi内测门禁与私聊邀请插件设计v2.md`](./Koishi内测门禁与私聊邀请插件设计v2.md)

---

## 测试分层（约定）

为避免“写得多但守不住”，本阶段只要求三类测试：

1. **契约测试**：对签名/幂等/错误码等“双方必须一致”的规则做固定向量验证。
2. **HTTP 集成测试**：使用 Go `httptest` 在进程内跑路由与中间件，使用临时 SQLite 数据库。
3. **纯业务单元测试**：门禁状态机、token 一次性/过期规则、outbox 状态机等，尽量不依赖 HTTP 与存储。

## 必须覆盖：E1 基础账号系统

### E1-T1：注册/登录/校验（HTTP 集成测试）

覆盖端点（以文档为准）：

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/validate`

必须验证：

- 注册重复、非法输入、错误结构稳定（code/message/fields）。
- 登录错误密码、账户被禁用/封禁时返回正确错误码与 HTTP 状态码。
- `validate` 对缺失/错误 Bearer 头的拒绝逻辑稳定。

最可能失败点：

- “用户状态机”分支在 login/validate/refresh（若实现）不一致，出现绕过或误拒绝。

### E1-T2：JWT payload 与过期语义（契约测试 + 集成测试）

必须验证：

- JWT 签名算法固定且不可被客户端指定。
- `exp/iat/issuer/sub` 等字段与文档一致。
- 过期 token、未来时间 token、issuer 不匹配 token 必须拒绝。

最可能失败点：

- 从“email 主键”迁移到 `user_id` 后，JWT payload 未统一，导致下游系统无法解析或权限判断错误。

### E1-T3：数据库迁移与唯一约束（集成测试）

必须验证：

- 迁移可重复执行（幂等）。
- `users/identities/sessions` 的核心唯一约束存在并生效（并发条件下也不产生重复记录）。

最可能失败点：

- 迁移不可重入导致部署/回滚时直接失败。

### E1-T4：Google OAuth Web Flow（HTTP 集成测试）

覆盖端点（以文档为准）：

- `GET /api/auth/oauth/begin/google`
- `GET /api/auth/oauth/callback/google`

必须验证：

- `begin` 必须生成一次性 `state` 并绑定到会话；缺失/重复/过期 state 必须拒绝（`INVALID_STATE`）。
- `callback` 在 code 交换失败时返回稳定错误（`OAUTH_CODE_EXCHANGE_FAILED`），且不产生用户/凭证副作用。
- OAuth 首登创建账号支持两条路径：
  - 携带有效 `invite_token` 时：允许创建用户，并在注册完成时绑定 QQ（从 invite_token 读取 issued_to_qq）。
  - 无 `invite_token` 时：允许创建用户但状态为 `pending_invite`（访问受限），并返回稳定提示（例如 `ACTIVATION_REQUIRED`）。
- `pending_invite` 的访问受限必须稳定：
  - 对需要内测资格/门禁的资源接口应拒绝（错误码稳定）。
  - 对激活接口（兑换 invite_token）应允许访问并可完成状态迁移。
- 登录/续期必须校验门禁：对已绑定 QQ 的账号，门禁不满足必须返回 `SUSPENDED_BY_GATE`。
- 成功/失败落地不得把 token 放入 URL（query/hash），采用站内 302 回跳并由页面提示。
- 错误响应 JSON 契约必须稳定：
  - 401/403/404 等非2xx响应体必须是 JSON，至少包含 `error`
  - 典型 `writeAPIError` 应包含 `code/message/error/fields?`，前端不会再出现“Unexpected token … is not valid JSON”

### E1-T5：Profile 兼容与数据源一致性（HTTP 集成测试）

覆盖端点：

- `GET /api/v1/user/profile`

必须验证：

- 使用新注册/新 OAuth 的 token 调用 profile 必须返回 200 且为 JSON
- 用户不存在时必须返回 404 且为 JSON（至少含 `error`），不可返回纯文本

## 必须覆盖：E2 内测资格系统（门禁 + 邀请）

### E2-T1：门禁规则与撤销策略（纯业务单元测试）

门禁硬规则：

- `gate_ok(qq) := in_group1(qq) && !in_group2(qq)`

必须验证：

- `eligible → suspended` 的触发条件正确（含“连续 N 次对账”策略）。
- `suspended → eligible` 的恢复条件正确（按实现约定，需在测试里锁定）。
- `banned` 不得被自动恢复。

最可能失败点：

- 事件驱动与快照对账的短暂不一致触发误封；二次确认计数/窗口逻辑写错。

### E2-T2：邀请 token 的一次性/过期/绑定规则（纯业务单元测试 + 集成测试）

必须验证：

- token 一次性：第二次兑换必失败且不产生副作用。
- token 过期：过期后必失败。
- token 绑定：若 token 绑定到目标 QQ，则“兑换者 QQ”不一致必失败。
- 兑换时二次校验门禁：门禁不满足必失败。

最可能失败点：

- token 未绑定到 QQ 或未做一次性校验，导致泄露后可被转卖/复用。

### E2-T3：审计日志落库（集成测试）

必须验证：

- 资格变更、邀请兑换、bot 写入等关键路径必落审计。
- 审计包含：`bot_id/request_id`（若来自 bot）、目标 QQ/user_id、动作类型、结果、时间。

最可能失败点：

- 只在成功路径记录审计，失败路径缺失导致不可排查与不可追责。

## 必须覆盖：E3 QQ 机器人集成（Bot API + Outbox）

### E3-T1：HMAC 签名固定向量（契约测试）

对以下要素做固定向量测试（golden vectors）：

- canonical string 的拼接规则：`METHOD + "\n" + PATH + "\n" + X-Timestamp + "\n" + X-Nonce + "\n" + SHA256_HEX(body)`
- `X-Timestamp` 单位（ms）与时间窗校验
- `PATH` 是否包含 query（建议不包含；若包含必须在测试里锁死）
- body hash 是否以“原始 body bytes”计算（避免 JSON 序列化差异）

最可能失败点：

- `\n`、timestamp 单位、body hash 取值形式任一不一致导致线上全量拒绝，但肉眼难排查。

### E3-T2：nonce 去重与 request_id 幂等（HTTP 集成测试）

必须验证：

- 时间窗外请求拒绝。
- 同 nonce 重放拒绝。
- 同 `(bot_id, request_id)` 重复提交必须幂等（不重复写入、不重复发任务、不重复审计）。

最可能失败点：

- 只做了 request_id 或只做了 nonce，导致可重放或重复副作用。

### E3-T3：群快照写入与判重（集成测试）

覆盖端点：

- `POST /api/v1/bot/qq/snapshot`

必须验证：

- `snapshot_hash` 判重策略正确（重复快照不触发重复计算/重复写入）。
- 快照规范化（排序/去重）一致，hash 可稳定复现。

### E3-T4：Outbox pull/ack 状态机（集成测试，含并发）

覆盖端点：

- `POST /api/v1/bot/outbox/pull`
- `POST /api/v1/bot/outbox/ack`

必须验证：

- `types/limit/cursor` 行为稳定。
- 过期任务不会被下发。
- `ack` 的重复提交幂等且不会改变最终状态。
- 并发 `pull` 不导致同一任务被多次下发（或如果允许多次下发，必须在测试里明确并验证“只会产生一次有效发送”）。

最可能失败点：

- 任务被重复发送（并发拉取/重试导致），或任务卡死（拉取后永远不再出现）。

### E3-T5：端到端最小闭环（集成测试）

用 `httptest` 直接模拟 Koishi 行为：

1) 上报群快照（满足门禁的人应进入可邀请候选）  
2) 服务端生成 invite outbox 任务（或通过拉取可见）  
3) `pull` 拉取到任务  
4) `ack` 回写 sent/failed  

必须验证：

- 门禁不满足的人不会生成邀请任务。
- 已注册/已禁用/已封禁的人不会生成邀请任务。

## 最小验收测试包（优先跑，最能防回归）

若只保留最小集合以满足“最可能失败点”的验收，至少包含：

- Bot HMAC 契约固定向量测试（canonical_string + bodyhash + timestamp 单位）
- Bot API 重放/幂等测试（timestamp window + nonce + request_id）
- Outbox pull/ack 并发一致性测试（重复 pull/重复 ack/过期任务）
- 门禁状态机测试（连续 N 次对账撤销、禁止误封）
- 邀请 token 兑换规则测试（一次性/过期/绑定 QQ/二次门禁校验）
